## [같은 장애를 두 번 겪지 않기 위해, 배포 전에 리뷰합니다 — KRIS 개발기](https://tech.kakao.com/posts/831)
- 회사: 카카오
- 본문 요약: 사내 AI 코드 리뷰 서비스 코드버디(CodeBuddy)의 응답 품질을 측정하는 평가 체계를 세우고 나니 다음 질문이 따라왔다는 데서 출발합니다 — "그래서 이 리뷰가 실제로 무엇을 막아주고 있는가?" 코드버디는 PR을 요약·리뷰하고 개선안을 제안하며 정확도도 꾸준히 올랐지만, 리뷰가 보는 것은 어디까지나 "코드가 올바른가"였습니다. 배포 후에야 발견되는 장애는 코드가 틀려서가 아니라 이 조직에서 이전에 한 번 터졌던 방식으로 위험하기 때문에 생깁니다. 게이트는 이미 충분히 많은데도 장애 데이터가 다음 배포에 재사용되지 않는다는 문제의식에서 KRIS(배포 리스크 리뷰)가 나왔습니다. 설계에서 가장 먼저 정한 것은 **비목표**였습니다. 코딩 컨벤션·가독성 리뷰는 기존 코드 리뷰 도구의 몫, 보안 취약점 스캔은 기존 보안 도구의 몫, 성능 최적화 제안은 장애 유발 가능성과 직접 관련이 없어 제외, 전체 코드베이스 분석 대신 PR·배포 단위의 diff만 봅니다. 이유는 단순합니다 — 또 하나의 범용 리뷰 도구를 만들면 개발자에게는 읽히지 않는 코멘트가 하나 더 늘어나는 일일 뿐이고, 이미 여러 봇이 PR에 코멘트를 달고 있기 때문입니다. KRIS의 코멘트가 읽히려면 "우리 조직과 개인의 기억에서만 나올 수 있는 문장"이어야 했습니다. 처리 파이프라인은 `Compare Provider → Policy RAG → LLM Severity 재평가 → 결과 전달` 4단계입니다. Compare Provider는 GitHub Compare API로 base/compare 참조를 조회해 변경 파일과 diff를 만들고(배포시스템에서는 절차서에 지정된 참조, PR에서는 base SHA와 head SHA 사용), Policy RAG는 diff를 컨텍스트로 관련 정책 규칙을 벡터 검색한 뒤 규칙마다 정의된 판정 로직으로 변경 내용을 직접 대조합니다. 여기가 핵심 설계 지점으로, **검색은 "어떤 규칙을 볼 것인가"를 좁히는 데만 쓰고 실제 위반 여부는 결정론적 판정 로직이 결정**합니다. 그 다음 LLM이 규칙의 기본 심각도를 시작점으로 diff 전체 문맥을 보며 3축으로 심각도를 재평가합니다. 정책을 만드는 일은 더하는 게 아니라 덜어내는 일이었다는 회고, 그리고 전사 공통 룰이 놓치는 것·애초에 알 수 없는 것이 있어 컬렉션을 조직별로 분리했다는 대목이 이어집니다. 전달 접점은 배포시스템과 GitHub PR 두 곳이며, 개발자의 흐름을 끊지 않는 위치에 붙이는 것을 원칙으로 삼았습니다. 다음 이야기는 설정값에서 소스코드로 범위를 넓히는 것.
- 주목할 point: **"장애는 왜 늘 배포 후에 발견될까"에 대한 답이 "게이트가 부족해서"가 아니라 "장애 데이터가 다음 배포에 쓰이지 않아서"였다**는 진단이 이 글의 출발점입니다. 리뷰 도구를 하나 더 만드는 대신, 이미 겪은 장애의 기억을 정책으로 만들어 배포 직전에 되돌려주는 쪽을 택했습니다. 두 번째는 **비목표를 먼저 정한 설계**입니다. "다른 도구가 할 수 있는 말은 하지 않는다"는 기준은 봇 코멘트가 포화된 PR에서 읽힘을 확보하는 유일한 전략에 가깝습니다. 세 번째는 **RAG를 판정이 아니라 후보 축소에만 쓴 구조** — 벡터 검색으로 관련 규칙을 좁히고, 위반 여부는 규칙에 딸린 결정론적 로직이 판정하며, LLM은 그 위에서 심각도만 재조정합니다. LLM에게 "이게 위반인가"를 묻지 않기 때문에 오탐이 줄고 판정 근거를 설명할 수 있습니다. 네 번째는 **전사 공통 룰의 한계를 인정하고 컬렉션을 분리한 것** — 조직마다 장애의 결이 다르므로 공통 룰이 놓치는 것과 애초에 알 수 없는 것을 구분해 정책 소유권을 내렸습니다. AI 코드 리뷰를 이미 굴리고 있는데 "그래서 뭘 막았나"를 답하지 못하는 팀이라면 그대로 가져다 쓸 수 있는 프레임입니다.

## [서버 개발자가 헥사코드를 몰라도 되게 만들기](https://devblog.kakaostyle.com/ko/2026-08-31-1-no-more-hex-code-on-server/)

## [DynamoDB 핫 파티션을 해결하는 3가지 방법 (4): 쓰기 샤딩](https://tech.channel.io/kr/articles/f1121e63)
- 회사: 채널톡
- 본문 요약: 시리즈 4편으로, User 테이블의 member GSI가 `channelId` 단위로 쓰기가 집중되면서 발생한 핫 파티션과 쓰로틀링을 쓰기 샤딩으로 푼 과정입니다. 문제의 심각성은 GSI 하나가 느려지는 데서 끝나지 않았다는 데 있습니다. GSI 쓰로틀링이 Back-Pressure를 만들어 **User 테이블 본체의 쓰기까지 거부되고, 결국 Boot 요청 실패로 이어질 위험**이 있었습니다. 원인 분석 결과 단일 `channelId`로 쓰기가 모이면서 DynamoDB 물리 파티션의 1,000 WCU 한계에 먼저 도달하는 구조였고, 기존 조회 패턴은 `channelId`와 `memberId`가 모두 있어 단건 조회는 가능했지만 쓰기 분산은 전혀 되지 않았습니다. 해결은 `memberId`로 suffix를 계산해 `channelId`와 조합하는 **결정적(deterministic) 쓰기 샤딩**입니다. 조회 시점에도 같은 입력으로 같은 샤드를 재현할 수 있어 스캐터-개더 없이 단건 조회가 유지됩니다. 저장·조회·백필 세 경로의 샤드 계산 규칙이 어긋나면 곧바로 데이터 불일치가 되므로 공통 프레임워크로 규칙을 한 곳에 통일했습니다. 마이그레이션은 기존 GSI에서 신규 샤드 GSI로 단계적 전환 후 검증하고 제거하는 방식이며, 백필 과정에서는 별도의 함정이 있었습니다 — DynamoDB Export 파일의 레코드 순서가 비슷한 키를 연속 처리하게 만들어 **Rolling Hot Partition**(핫스팟이 파티션을 옮겨 다니며 계속 발생)이 생겼고, AWS Glue 백필에 Rate Limit과 Shuffle을 함께 적용해 해소했습니다. 적용해볼 점으로 조회 입력만으로 대상 샤드를 재현할 수 있는지를 먼저 확인할 것, 쓰기량뿐 아니라 읽기 비용과 백필 운영 비용까지 함께 고려할 것을 제시합니다.
- 주목할 point: **쓰기 샤딩의 성패는 "조회 입력만으로 샤드를 되찾을 수 있는가"에서 갈린다**는 점이 가장 실용적인 기준입니다. 랜덤 suffix를 쓰면 쓰기는 완벽히 분산되지만 조회가 N개 샤드 전체를 훑는 스캐터-개더가 되어 읽기 비용이 N배가 됩니다. 여기서는 이미 조회 시점에 갖고 있는 `memberId`를 해싱해 샤드를 정했기 때문에 단건 조회 성능을 그대로 유지했습니다. 두 번째는 **GSI 쓰로틀링이 베이스 테이블 쓰기를 막는다**는 DynamoDB 특유의 전파 경로 — 이걸 모르면 "GSI 하나 느려진 것뿐"으로 오판하다 Boot 실패라는 서비스 장애를 만나게 됩니다. 세 번째는 **백필의 Rolling Hot Partition**이라는, 겪어보지 않으면 예측하기 어려운 함정입니다. Export 파일은 키 순서대로 정렬돼 있으므로 그대로 읽으면 특정 파티션에 쓰기가 몰리고, 진행에 따라 핫스팟이 이동합니다. Shuffle과 Rate Limit이 함께 필요한 이유가 여기 있습니다. 네 번째는 **샤드 계산 규칙을 공통 프레임워크로 강제한 것** — 저장·조회·백필 세 경로 중 하나만 규칙이 어긋나도 조용히 데이터를 잃습니다.
