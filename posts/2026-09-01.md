## [모놀리식인데, 도메인 하나만 따로 띄웁니다](https://flex.team/blog/2026/09/01/backend40)
- 회사: flex
- 본문 요약: `./gradlew :issue:standalone-app:bootRun` 한 줄이면 이슈 도메인만 따로 뜨고, MySQL 컨테이너가 올라오고, 스키마가 적용되고, 샘플 데이터가 채워지고, Swagger UI와 간단한 화면까지 서빙됩니다. Gateway도 인증 서버도 다른 도메인 서비스도 없는데 비즈니스 로직은 프로덕션과 같은 코드로 돕니다. 이 글이 말하려는 건 편리함이 아니라 **한 프로세스로 뜨는 모놀리식 안에서 기동 단위를 도메인 하나로 좁혔다**는 사실입니다. 보통 모놀리식은 부분만 떼어 세울 재료 자체가 없지만, 모듈러 모놀리식은 도메인·계층별로 빌드 모듈이 나뉘어 있어 **골라 담을 수 있습니다**. 왜 중요한가는 기동 시간을 세어 보면 드러납니다 — 전체 90초, 슬라이스 20초, 고침-확인 순환 하루 20회로 가정하면 하루 약 23분, 한 달이면 여덟 시간(개발자 한 명이 한 달에 하루치 근무를 기동 화면만 보며 보내는 셈)이며, 여기에 90초 동안 주의가 새면 맥락을 다시 잡는 비용이 더 붙습니다. 저자는 특히 **AI 에이전트에게 이 순환의 길이는 곧 일할 수 있느냐 없느냐의 문제**라고 짚습니다. 조립의 청사진은 빌드 파일에 있고 세 가지 결정이 담깁니다 — ① 이슈 도메인의 api/service/infrastructure/저장소 어댑터만 끌어옴, ② 채번처럼 이슈가 혼자 설 수 없는 딱 그만큼만 크로스 도메인 의존 허용(이 목록이 곧 "이슈 도메인이 진짜 뭘 필요로 하는가"의 명세), ③ 전이 의존으로 딸려 오는 프로덕션 전용 모듈은 이름으로 콕 집어 배제. 조립 목록에 없는 도메인은 클래스패스에 아예 없으니 실수로도 못 씁니다. 채번을 데려오면 "번호 발급 + 저장"을 하나의 원자적 작업으로 묶어야 하는데(Unit of Work), 이 경계를 프레임워크 트랜잭션 애너테이션에 암묵적으로 맡기지 않고 `execute { 채번과 저장 }` 꼴의 **도메인이 소유하는 슬롯**으로 코드에 드러냈습니다. 계약은 어느 배포에서나 같지만 그걸 지키는 부품은 조립에 따라 달라집니다 — 한 앱이면 로컬 단일 트랜잭션, 채번이 외부 API로 떨어져 나가면 Saga 보상 트랜잭션이나 Outbox. **핵심은 이 차이가 비즈니스 코드에 한 줄도 새지 않는다**는 점입니다. 자기 완결성도 챙겼습니다 — 시드 데이터를 저장소에 직접 꽂지 않고 도메인 UseCase를 호출해 만들어(채번이 돌고 상태 전이 규칙이 검사되고 이벤트가 발행됨) 시드 자체가 도메인 검증을 통과한 결과물이 되게 했고, MySQL은 빌드 태스크의 컨테이너 선언 한 줄로 뜨며 접속 정보가 자동 주입됩니다. 마지막으로 이 사고방식이 여러 축에서 반복된다고 정리합니다 — 시간을 갈아 끼우기(특정 시점인 것처럼 앱 실행), 공간을 갈아 끼우기(요청 목적지를 통제된 대역으로), 구조를 갈아 끼우기(standalone). 관통하는 발상은 "검증에 필요한 최소한만 진짜로 두고 나머지는 교체 가능한 경계 뒤로 민다"이고, Port/Adapter는 그 자리를 구조 축에서 제공하는 장치였다는 것입니다.
- 주목할 point: **모듈러 모놀리식의 실질적 배당금이 "나중에 MSA로 쪼갤 수 있음"이 아니라 "지금 당장 검증 단위를 고를 수 있음"이라는 재정의**가 이 글의 가장 값진 지점입니다. 모듈러 모놀리식을 도입해 놓고도 여전히 전체를 띄워 검증한다면 얻은 게 코드 정리뿐일 수 있습니다. 두 번째는 **기동 시간을 감이 아니라 산수로 환산한 것** — 회당 70초는 무시할 만해 보이지만 하루 20회 × 20일이면 여덟 시간이고, 여기에 컨텍스트 스위칭 비용이 추가로 얹힙니다. 그리고 "AI 에이전트에게 루프 길이는 일할 수 있느냐의 문제"라는 관점은 앞으로 개발 환경 설계의 기준이 사람의 인내심에서 에이전트의 반복 가능성으로 옮겨간다는 신호로 읽힙니다. 세 번째는 **트랜잭션 경계를 애너테이션이 아니라 도메인 소유 슬롯으로 뽑아낸 설계**입니다. `@Transactional`에 암묵적으로 기대면 배포 형태가 바뀔 때 비즈니스 코드가 흔들리지만, 슬롯으로 뽑아 두면 로컬↔Saga↔Outbox 교체가 조립 지점에서 끝납니다. 이 한 수 덕분에 "MSA로 분리하더라도 이슈를 만드는 로직은 한 줄도 안 고친다"가 성립합니다. 네 번째는 **시드를 저장소가 아니라 UseCase로 만든 결정** — 사소해 보이지만, 저장소에 직접 꽂은 시드는 도메인 규칙을 우회한 데이터라 검증 환경의 신뢰도를 조용히 갉아먹습니다. 검증 환경을 만들면서 검증 경로로 데이터를 만든다는 발상은 그대로 훔쳐 쓸 만합니다. 마지막으로 "언제 쪼갤지는 부하가 정하고, 어떻게 쪼갤지는 이미 조립이 답해 둔 셈"이라는 문장은 MSA 전환을 앞둔 팀이 지금 무엇을 해 둬야 하는지에 대한 가장 간명한 답입니다.

- 본문 요약: 사용자가 자신의 환경에 직접 **다운로드해서 설치하고 업데이트하는** Vizend Platform이라는 특수 조건에서 DB Migration을 운영한 경험입니다. 일반 웹 서비스라면 배포 파이프라인의 일부로 SQL을 실행하면 되지만, 여기서는 개발자가 사용자 환경의 DB에 직접 접근할 수 없으므로 애플리케이션이 스스로 업데이트될 때 **Runtime에 스키마도 함께 자동 업데이트**되어야 했습니다. Flyway를 붙이고 `ddl-auto: validate`로 Hibernate는 검증만 하게 구성했지만, 여러 버전을 거치며 "SQL을 순서대로 자동 실행한다"만으로는 안전한 마이그레이션이 안 된다는 걸 겪습니다. 정리된 세 가지 질문은 — 다시 실행해도 안전한가(멱등성), 문제 생기면 되돌릴 수 있는가(Rollback), 되돌리는 데 필요한 데이터가 남아 있는가(Backup). **멱등성**: Versioned Migration은 성공하면 재실행되지 않지만, 일부 SQL 실행 후 오류, 장애 복구 중 수동 재실행, 설치 환경마다 다른 DB 상태를 가정해야 하므로 `IF (NOT) EXISTS`를 기본 원칙으로 삼되 — 여기서 중요한 단서가 붙습니다 — `ADD COLUMN IF NOT EXISTS status VARCHAR(20)`은 이미 `status INTEGER`가 있으면 오류 없이 끝나지만 DB는 기대 상태가 아닙니다. 그래서 "두 번 실행해도 오류가 안 난다"가 아니라 **"몇 번을 실행하든 최종 상태가 동일한가"**를 멱등성의 기준으로 잡았습니다. **Rollback**: Incremental Migration마다 대응 Rollback Script를 별도 디렉터리에 함께 작성(Flyway가 자동 실행하지 않고 담당자가 확인 후 실행). **Backup**: 컬럼을 삭제한 뒤 되돌릴 때 `ADD COLUMN`으로 스키마는 복구돼도 데이터는 이미 사라졌으므로 **Schema Rollback과 Data Rollback은 다른 문제**임을 명시하고, 기존 컬럼을 바로 지우지 않고 `RENAME COLUMN A TO A_7_1_3` 식으로 버전을 포함한 이름으로 보존하거나 `CREATE TABLE user_7_1_3 AS SELECT *`로 백업 테이블을 만드는 규칙을 세웠습니다. 결정적으로 **Forward를 먼저 만들고 나중에 Rollback을 고민하면 이미 데이터가 삭제된 뒤일 수 있으므로, 작성 시점에 Backup·Rollback을 함께 설계**하도록 가이드에 못 박았습니다. 두 번의 시행착오도 상세합니다 — ① **Baseline 관리**: 신규 설치가 수십 개 마이그레이션을 처음부터 다 거치는 낭비를 줄이려 Minor 버전별 스냅샷 SQL을 따로 관리했더니 동일 스키마를 Incremental과 Baseline 두 곳에서 사람이 정합성을 유지해야 하는 구조가 됐고(자동화하면서 수동 관리 요소를 새로 만든 셈), 이를 각 Minor 버전의 patch 0을 `V7_1_0__Initial.sql`로 두는 **Initial Migration** 방식으로 바꿔 신규 설치 시작점을 마이그레이션 체계 안에 흡수했습니다. ② **여러 개발자 동시 작업**: 서로 다른 브랜치에서 최신이 V7_2_2인 시점에 각자 V7_2_3을 만들면 머지 시 버전이 충돌하고, 이미 실행된 환경이 있으면 flyway_schema_history 때문에 단순 rename으로 안 끝납니다. 또 V7_2_8이 V7_2_7보다 먼저 배포되는 순서 역전도 발생합니다. 결론은 **Migration Version은 파일 정렬 기준이 아니라 DB 스키마가 변경되는 실제 순서를 나타내는 운영 정보**이며, Git 브랜치 머지와 릴리스 프로세스도 DB Migration의 일부라는 것입니다.
- 주목할 point: **"Flyway를 쓴다고 마이그레이션이 자동으로 안전해지지 않는다"**는 문장이 이 글의 핵심입니다. Flyway는 무엇이 실행됐는지 기록하고 순서대로 실행해줄 뿐, 반복 실행에 안전한지·복구 가능한지·롤백이 준비됐는지는 판단해주지 않습니다. 두 번째는 **멱등성의 정의를 "오류 없음"이 아니라 "최종 상태 동일"로 잡은 것** — `IF NOT EXISTS`가 타입이 다른 기존 컬럼을 조용히 통과시키는 예시는 실제로 겪기 전에는 놓치기 쉬운 함정이고, 이 구분 하나가 "성공했는데 앱이 안 도는" 상황을 막습니다. 세 번째는 **Backup과 Rollback을 하나의 작업으로 묶은 원칙**입니다. Forward를 다 만든 뒤 롤백을 고민하기 시작하면 순서상 이미 늦고, 그래서 "데이터 변경·삭제가 있는 작업은 Backup 필수"를 가이드에 규칙으로 박아둔 것이 실무적으로 가장 이식성 높은 부분입니다. 백업 오브젝트 이름에 마이그레이션 버전을 넣는 컨벤션(`user_7_1_3`)도 그대로 쓸 만합니다. 네 번째는 **Baseline 스냅샷의 이중 관리 함정** — 자동화를 도입하면서 옆에 수동 관리 지점을 만들면 결국 그 지점이 깨집니다. "신규 설치 결과와 기존 DB 업데이트 결과가 달라질 수 있다"는 건 발견하기도 어렵고 발견 시점엔 이미 늦은 종류의 버그입니다. 다섯 번째, **DB 마이그레이션이 SQL 문제가 아니라 브랜치 전략 문제**라는 결론은 팀 규모가 커질수록 체감이 큽니다. 머지 직전 최신 버전 확인, 중복 확인, 배포 순서와 버전 순서 일치 확인, 이미 실행된 마이그레이션 불변 — 이 네 줄은 그대로 PR 체크리스트에 넣어도 됩니다. 특히 "문제 생겼을 때 repair를 단순 버전 정리 목적으로 쓰지 않는다"는 항목은 사고를 키우지 않는 안전장치입니다.
