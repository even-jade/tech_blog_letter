- 본문 요약: Oozie XML로 관리되던 1,200여 개 데이터 파이프라인과 2021년 공식 지원이 종료된 Sqoop을 Airflow와 Spark로 전면 전환한 AI Data Platform팀의 경험입니다. 기술 부채, 직관적이지 않은 Oozie UI와 XML 하드코딩 운영 부담, 분할 불가능한 Text+Gzip 포맷과 Sqoop 고정 Mapper가 만드는 Small File 문제가 배경이었습니다. 공통 설정(base.yaml)과 개별 설정(dag.yaml)을 분리한 DAG Factory 패턴으로 dag.yaml만 쓰면 Spark 입수 → Hive 테이블/파티션 생성 → .done 마커 생성 워크플로우가 자동 배포되도록 했고, 콜백으로 Teams·메일 알림과 메트릭 수집을 붙였습니다. 자체 입수 프레임워크 Oggre는 DBA_SEGMENTS→USER_SEGMENTS→ALL_TABLES 3단계 폴백으로 테이블 용량을 산정해 256MB를 기준으로 단일(One-Pass)/병렬(Two-Pass) 추출을 분기하고, 숫자형 PK/인덱스 컬럼을 1순위로 파티션 키를 자동 선정합니다. Spark는 파티션 수와 동시 실행 태스크 수가 분리돼 있어 Executor×코어(8개)로 DB 동시 커넥션 상한이 고정된다는 점이 Sqoop과의 결정적 차이입니다. 날짜형 파티션 키는 Spark 내부 형변환에서 드라이버 타입 불일치가 나서 partitionColumn 대신 Predicates API로 TO_DATE 조건절을 직접 생성해 주입했고, NULL은 별도 파티션으로 수집했습니다. JDBC 추출(Phase 1)과 셔플·정렬(Phase 2)을 temp_path 경계로 분리해 fetchsize=20,000과 memory.fraction=0.8이 충돌하지 않는 이유를 메모리 영역별로 설명하며, temp_path의 실측 용량으로 파일 개수를 산정(Oracle 카탈로그 158GB vs Parquet 실제 19.7GB, 8배 차이)한 뒤 repartitionByRange+sortWithinPartitions로 256MB 균등 파일을 만들었습니다. 결과적으로 입수 시간 25~70% 단축, 260KB 테이블이 4개 파일→1개 파일, 5GB짜리 4개 파일→240~280MB 다수 파일로 개선됐고, 정렬 컬럼 특정 값 조회는 939.8초→14.1초(66.8배), 결과가 많은 조회는 299.7초→31.0초(9.7배) 빨라졌습니다.
- 주목할 point: 원천 DB 용량이 아니라 Parquet 압축 후 실측 용량으로 파일 개수를 정해야 한다는 근거(8배 차이), 날짜형 파티션 키의 형변환 이슈를 Predicates API로 우회한 코드, 그리고 Row Group Pruning 효과가 정렬 기준 컬럼으로 조회할 때만 크게 나타난다는 실측 분석이 실무적으로 유용합니다. Spark 메모리를 Execution/User 영역과 Phase로 나눠 설명한 부분은 JDBC 입수 튜닝의 좋은 참고 자료입니다.
