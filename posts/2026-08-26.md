## [Vision Transformer 구현 — TensorFlow/Keras로 손글씨(MNIST) 분류하기](https://devocean.sk.com/blog/techBoardDetail.do?id=168459&boardType=techBlog&isShared=Y)
- 회사: 데보션
- 본문 요약: "이미지를 작은 조각(패치)들로 잘라서, 각 패치를 문장 속 단어처럼 취급하고 Transformer로 처리하자"는 ViT의 핵심 아이디어를 MNIST 분류 예제로 개념 → 수식/구조 → 코드 → 실행 결과 순서로 11단계에 걸쳐 구현합니다. CNN 없이 순수 Attention만으로 이미지를 이해하는 과정을 확인하는 것이 목표이며, 전체 소스가 글 말미에 첨부돼 있습니다. 하이퍼파라미터는 학습용으로 크게 줄여 hidden=8, head=2, encoder=6, patch=7(7×7=49패치), token=50입니다. 흐름은 28×28×1 → 패치화(49×16) → Linear 임베딩(49×8) → CLS 토큰 추가(50×8) → 위치 임베딩 → Encoder×6 → Global Average Pooling(1×8) → Dense(10)+Softmax입니다. 각 단계마다 텐서 모양 변화를 배치 차원과 함께 명시하고, `tf.image.extract_patches`의 sizes/strides/rates/padding 인자를 하나씩 풀어 설명합니다(28×28 초콜릿 판을 4×4로 자르는 비유). `PatchLayer` 안에 `extract`를 중첩한 이유를 클로저 관점에서 설명하고, **MY_PATCH는 28의 약수(1,2,4,7,14,28)여야 한다**는 점 — 5로 두면 `28//5=5`라 마지막 3픽셀이 `padding='VALID'` 때문에 에러 없이 조용히 버려진다는 함정 — 도 짚습니다. 특히 값진 것은 저자가 명시한 세 가지 수정 이력입니다. ①(심각) x_train만 전처리하고 x_test를 빠뜨려 `evaluate()`에서 모양 불일치가 나던 문제 — 두 데이터셋은 항상 같은 규칙으로 함께 전처리해야 합니다. ②(설계 버그) `encoder_block` 안에서 LayerNormalization 레이어 **객체 하나를 어텐션 앞과 MLP 앞 두 곳에서 재사용**하던 문제 — Keras는 레이어 객체를 재사용하면 같은 γ·β를 공유하므로 표준 Pre-Norm 구조(z' = z + MSA(LN(z)), z'' = z' + MLP(LN(z')))와 달라지고 표현력이 줄어듭니다. norm1/norm2로 분리했습니다. ③(설계 노트) CLS 토큰을 "패치들의 평균을 Dense로 변환"해 만들면 입력 내용에 종속되어 시작해 원 논문 의도와 어긋나므로, 입력과 무관하게 독립 학습되는 파라미터를 `add_weight`로 만들고 배치 크기만큼 `tf.tile`하는 표준 방식으로 교체했습니다. Step 9에서는 원 논문이 CLS 토큰만 뽑아 쓰는(`x[:, 0]`) 반면 이 코드는 50개 토큰 전체를 GAP으로 평균낸다는 차이도 "두 방식 모두 통용되지만 서로 다른 설계 선택"이라고 구분해 밝힙니다. 각 부품을 TDD로 assert 검증하며 만든 점도 특징입니다.
- 주목할 point: 논문 도식만으로는 잘 안 잡히는 ViT의 텐서 흐름을 모양 변화 중심으로 추적하는 구성이 실용적이지만, 이 글의 진짜 값은 **"자주 틀리는 지점"을 수정 이력으로 명시했다는 데** 있습니다. LayerNorm 객체 재사용은 Keras를 쓰는 사람이 흔히 저지르면서 에러가 안 나서 못 잡는 종류의 버그이고, x_test 전처리 누락도 마찬가지입니다. MY_PATCH가 28의 약수가 아닐 때 `padding='VALID'`가 가장자리를 조용히 버린다는 지적, CLS 토큰 vs GAP의 설계 선택 구분도 튜토리얼 코드에서 잘 다뤄지지 않는 대목입니다. 글 말미의 DEVOTEE(AI) 댓글이 던진 "CLS 토큰만 쓰기 vs 전체 토큰 GAP, 어느 쪽을 선호하는가"라는 토론 주제도 함께 읽어볼 만합니다.

## [AI-Ready Data Platform으로 가는 세 가지 질문](https://blog.afinit.com/ai-ready-data-platform)
- 회사: 밸런스히어로
- 본문 요약: 어피닛 데이터 엔지니어링 팀이 AI를 데이터 플랫폼의 **새로운 소비자(Data Consumer)**로 규정하고, 그 소비자를 받아들이기 위해 필요한 조건을 세 질문으로 정리한 글입니다. 출발점은 전제의 변화입니다. 사람은 테이블 이름이 모호해도 조직 경험으로 의미를 추론하거나 담당자에게 물어볼 수 있었고, 기존 모델·서비스는 어떤 데이터를 어떻게 쓸지가 개발 단계에 이미 정해져 있었습니다. 반면 AI Agent는 스스로 탐색하고 그 결과로 다음 행동을 판단하지만 조직의 암묵적 맥락은 갖고 있지 않습니다. 저자는 "AI가 SQL을 잘 쓰면 되지 않나"라는 기대에 구체적인 반례를 듭니다 — **각 쿼리가 독립적으로 90% 정확하다 해도 10개가 모두 맞을 확률은 약 35%**이고, 여러 조회와 판단을 연속하는 Agent에서는 작은 오류가 빠르게 누적됩니다. 더 근본적으로 `loan_status = 3`을 발견했을 때 SQL을 만드는 건 쉽지만 3이 연체인지 상환 완료인지는 스키마만으로 확정할 수 없습니다. ① **Context**: 카탈로그·메타데이터와 시멘틱 레이어. 사내 Data Lake Manager(DLM)를 운영하며 크롤러가 주요 운영 스키마의 Glue Data Catalog를 주기적으로 훑어 컬럼명·타입·설명·신선도·최종 갱신 시각·스키마 드리프트까지 모읍니다(현재 36개 스키마, 1,600여 개 활성 데이터셋). Amundsen·OpenMetadata도 도입해봤지만 핵심 기능을 직접 구현해 운영 중입니다. 시멘틱 레이어는 컬럼마다 설명을 붙이는 방식이 지속 가능하지 않다고 보고 User·Loan 같은 비즈니스 개념과 실제 테이블·컬럼을 연결하는 구조를 제한된 도메인에서 PoC 중이며, "의미를 만드는 일보다 그 의미를 검증 가능한 상태로 유지하는 일이 더 어렵고, 잘못된 의미는 오히려 데이터 신뢰를 떨어뜨린다"는 경계도 명시합니다. ② **Governance**: "AI에게 데이터를 어떻게 더 많이 보여줄까"보다 "어디까지 보여줘도 되는가"를 먼저 정의하는 것 — 접근을 여는 것보다 경계를 세우는 일이 먼저입니다. 컬럼명 단서와 값 패턴의 규칙 기반 분석, 오픈소스 PII 탐지 프레임워크 Microsoft Presidio, 학습된 분류 모델을 조합해 민감정보 컬럼을 식별하고 민감도 태그를 부여하며, 이 태그를 Lake Formation과 동기화해 Tag-Based Access Control로 강제합니다. 원칙은 **권한 기본값을 '차단'에 두는 것**입니다. ③ **Interface**: 도구마다 DB에 직접 붙으면 추적이 어렵고 통제 수준도 달라지므로 Data Platform MCP로 접근을 공통화하되, 디스커버리(메타데이터 탐색, 통제 수준 낮음)와 실제 데이터 조회(identity·scope·audit 필요)를 명확히 구분합니다. 후자는 Query Gateway를 거쳐 실행하도록 설계 중이며, "사용자의 권한은 Agent가 가질 수 있는 권한의 **상한선일 뿐 실제 위임 범위와 같을 필요는 없다**"는 구분을 두 번 강조합니다. 현재 상태는 Context(카탈로그 운영 중·시멘틱 레이어 PoC), Governance(PII 탐지·태깅 운영 중·Lake Formation 적용 확대 중), Interface(카탈로그 API 운영 중·MCP와 Query Gateway 구축 중)로 정직하게 표로 정리했습니다. 마지막으로 같은 문제가 플랫폼 운영에도 나타난다며 운영 신호와 팀 지식을 AI가 활용하도록 연결한 사내 Agent를 실제 환경에서 쓰고 있다고 예고합니다.
- 주목할 point: "AI 도입"을 모델 문제가 아니라 데이터 플랫폼의 구조 문제로 재정의한 프레이밍이 핵심이고, **0.9^10 ≈ 35%**라는 단순한 계산 하나가 "SQL 정확도가 높으니 괜찮다"는 낙관을 정확히 깨뜨립니다. 특히 눈에 띄는 것은 **"사람의 권한을 정의하는 것과 그 권한을 Agent에게 위임하는 것은 같은 문제가 아니다"**라는 구분 — 사내 데이터에 LLM을 붙이는 조직 대부분이 두 가지를 동일시하는 지점입니다. 완성된 아키텍처를 자랑하는 대신 무엇이 운영 중이고 무엇이 PoC인지 표로 밝힌 정직함, 그리고 시멘틱 레이어가 잘못되면 오히려 신뢰를 깎는다는 자기 경계도 참고할 만합니다. 같은 날 올라온 KT 클라우드의 MCP Hub 글과 문제의식이 거의 겹쳐 함께 읽으면 좋습니다.

"제 주민번호는 951016-1234567이에요" 같은 메시지가 그대로 DB에 쌓이면 대화를 열어볼 수 있는 누구나 원문을 볼 수 있고, 이는 고객사의 개인정보 처리 기준과 내부 감사에 부담이 되며 엔터프라이즈 도입을 가로막는 벽이기도 했습니다. 기능은 채널 설정에서 켜면 기본 규칙 7가지(신용카드 번호, 개인 식별자, 이메일, 전화번호, IP 주소 등)에 커스텀 규칙 최대 10개를 더해 채널당 최대 17개 규칙을 적용합니다. 저자는 "기능 자체는 정규식으로 값을 찾아 별표로 바꾸는 단순한 작업이고, 정작 시간이 오래 걸린 건 규칙을 어디까지 적용할지 정하는 쪽"이었다고 밝힙니다. ① **저장 전에, 그리고 한 곳에서**: 조회 시 마스킹은 되돌릴 수 있다는 장점이 있지만 원문이 DB에 남아 검색·웹훅·푸시 알림 등 뒤에 이어지는 모든 것이 유출 경로가 됩니다. 그래서 저장 전 마스킹을 택했고, 그 대신 "저장으로 가는 길이 하나여야 한다"는 조건이 붙어 생성이든 편집이든 같은 파이프라인 앞단에 마스킹을 두었습니다. 여기에 fail-secure를 더해 마스킹 도중 예외가 나면 메시지 저장 자체가 실패하도록 했습니다(웹훅 같은 후속 처리도 함께 멈춤). ② **못 잡아도, 잘못 잡아도 되돌릴 수 없다**: 전화번호는 하이픈·공백·점·국가번호(+82, +81, +1) 등 표기 변형을 최대한 규칙에 담았고, 반대로 형식만 보고 판단하면 오탐이 나는 카드번호는 **카드사 BIN으로 실제 발급 가능한 번호대인지 확인하고 Luhn 체크섬으로 한 번 더 검증**합니다(`4539-1234-5678-9998`은 체크섬 불일치로 통과, `9812-...`는 존재하지 않는 BIN으로 통과). 표시 방식은 값을 통째로 들어내면 "무언가 있었다"는 사실까지 사라져 상담사가 가려진 건지 애초에 없었던 건지 구분할 수 없으므로, 원본 길이를 유지한 채 매칭 구간 전체를 같은 개수의 별표로 바꿉니다. 규칙 충돌은 우선순위를 매기려면 어떤 규칙이 더 중요한지 정해야 하는데 채널마다 커스텀 규칙이 다르므로, 우선순위 없이 **매칭 구간을 모두 합쳐서 가리는** 쪽을 택했습니다(조금 과하게 가려지더라도 보안 관점에서 더 넓게). 정규식은 눈으로 봐선 무엇을 잡을지 알기 어려워 등록 화면에 테스트 버튼을 넣었습니다. ③ **모든 메시지가 이 길을 지난다**: 경로를 하나로 모은 대가로 모든 메시지가 마스킹 비용을 치릅니다. 예산 기준을 잡기 위해 트래픽과 기존 쓰기 지연을 실측했는데, 처음 예상과 달리 **시간대별 쓰기량이 10배 이상 차이 나도 p99 지연 차이는 1.2배 안쪽**이라 시간대는 큰 변수가 아니었습니다. 메시지 크기는 95% 이상이 500바이트 미만, 99%가 1.2KB 이하였지만 드물게 수백 KB짜리도 있었고 최악의 비용은 이들이 결정했습니다. 벤치마크(p95, 평소 쓰기 경로를 예산 1로) 결과 기본 규칙만이면 100KB에서도 예산의 0.2%인 반면, 복잡한 커스텀 규칙 10개를 더하면 1KB 1.6% → 5KB 8% → 10KB 15% → 50KB 82% → 100KB에서는 예산을 약 1.7배 초과했습니다(같은 100KB에서 기본 규칙 대비 800배 이상). 위험은 두 갈래로 갈렸습니다. **지수적 폭발(ReDoS)** — 관리자가 등록한 정규식이 그 채널의 모든 인입 메시지에 적용되므로 잘못된 패턴 하나가 폭발하면 상담 전체가 멈춥니다. JDK 기본 `java.util.regex`(백트래킹) 대신 입력 길이에 선형인 RE2 계열 `re2j`로 교체했고, `(.*?,){N}P` 패턴으로 검증한 결과 **쉼표 30개부터 JDK 엔진은 5초 넘게 멈춘 반면 re2j는 처음부터 끝까지 0.1ms 근처를 유지**했습니다. **선형 누적** — 엔진을 바꿔도 입력이 크면 비용은 길이에 비례해 쌓이므로 길이 상한을 두었습니다. 상한은 통과율과 비용을 나란히 놓고 정했는데, 통과율은 1KB에서 이미 98.6%이고 100KB까지 올려도 1.4%p밖에 오르지 않는 반면 비용은 몇 배씩 뛰다 100KB에서 예산을 넘겼습니다. 배포 후 처음 문제를 제기한 고객사뿐 아니라 보안 검토 때문에 도입을 미뤘던 고객사에서도 사용 중입니다.
- 주목할 point: **"개인정보 유출 위험을 줄이려고 만든 기능이 그 자체로 새로운 위험이 되지 않는 범위를 찾아야 했다"** — 이 한 문장이 글 전체를 요약합니다. 사용자 정의 정규식을 허용하는 순간 ReDoS가 곧 고객이 만드는 장애 요인이 되므로 RE2와 길이 상한은 선택이 아니라 전제조건이라는 점, 카드번호를 BIN+Luhn으로 이중 검증해 오탐을 줄인 점, 그리고 상한값을 감이 아니라 **통과율 곡선과 비용 곡선을 겹쳐 놓고** 정한 접근이 특히 실무적입니다. "몰리는 시간대가 제일 위험할 것"이라는 예상이 실측에서 틀렸다는 대목도 좋습니다 — 예산을 시간대 무관한 지표 하나로 잴 수 있게 만든 발견이었습니다. 저자의 마무리("문제는 얼마나 촘촘하게 지우느냐가 아니라 어디까지를 감당할 범위로 볼 것이냐")는 보안 기능 전반에 적용됩니다.

## [LLM은 왜 Graph DB를 필요로 할까?](https://blog.kyobodts.co.kr/2026/08/26/llm%ec%9d%80-%ec%99%9c-graph-db%eb%a5%bc-%ed%95%84%ec%9a%94%eb%a1%9c-%ed%95%a0%ea%b9%8c/)
- 회사: 교보DTS
- 본문 요약: 일반적인 RAG는 질문과 의미적으로 유사한 문서를 찾아 LLM의 Context로 넘기지만, 실제 기업 데이터는 독립적인 문서만으로 구성돼 있지 않고 고객–계약, 기업–투자자, 직원–프로젝트처럼 서로 관계를 맺고 있다는 문제 제기에서 출발합니다. 대표 예시는 **"A 기업에 투자한 펀드를 운용하는 운용사가 투자한 다른 기업은 어디인가?"** — 이 질문은 A 기업 관련 문서를 찾는 것이 아니라 기업 → 펀드 → 운용사 → 다른 기업으로 이어지는 관계를 탐색해야 합니다. Graph DB는 기업·펀드·운용사 같은 개체를 Node로, '운용한다'·'투자한다' 같은 관계를 Edge로 표현하며, RDB도 JOIN으로 관계를 조회할 수 있지만 Graph DB는 관계 자체를 중심으로 저장하고 탐색한다는 점이 다릅니다. Vector DB와의 비교를 표로 정리하는데, 검색 기준(의미적 유사성 vs Entity 간 관계), 주요 데이터(문서·Chunk vs Entity·Relationship), 적합한 질문("관련 내용은 무엇인가?" vs "무엇과 어떻게 연결되어 있는가?"), 대표 활용(Semantic Search·RAG vs 관계 탐색·Knowledge Graph)으로 나눕니다. 따라서 둘 중 하나를 고르기보다 질문 특성에 따라 함께 쓰는 Hybrid Retrieval이 현실적입니다. GraphRAG는 "A기업과 관련된 투자 리스크를 분석해줘"라는 질문에서 A기업이라는 Entity를 식별해 Graph를 탐색하고, 거기서 찾은 투자자·계열사·주요 인물 등 연결된 Entity를 기준으로 검색 범위를 확장한 뒤 Vector DB에서 관련 보고서를 추가로 검색하는 식으로 동작합니다 — 핵심은 Graph DB를 RAG에 얹는 것이 아니라 **문서의 의미적 유사성과 데이터의 관계를 함께 활용해 더 풍부한 Context를 구성하는 것**입니다. 나아가 Agentic AI에서는 LLM이 요청을 분석해 필요한 도구를 판단하므로, "A기업의 투자 리스크와 관련 기업의 최근 실적을 분석해줘"를 Graph Search Tool(투자자·관계기업 탐색) → SQL Tool(실적 데이터 조회) → Vector Search Tool(보고서 검색) → 종합 순으로 나눠 처리할 수 있고, 이때 Graph DB는 저장소가 아니라 **Agent가 필요할 때 호출하는 관계 탐색 Tool**이 됩니다. 활용 분야로는 금융·투자(기업–주주–펀드–운용사–계열사), 보험(고객–계약–피보험자–사고–청구의 이상 패턴 분석), 사내 지식 검색(직원–조직–프로젝트–기술–문서 Knowledge Graph)을 듭니다. 마지막 절 제목이 **"Graph DB가 항상 정답은 아니다"**인 점이 인상적인데, 단순 FAQ·문서 검색처럼 유사성이 중요한 서비스는 Vector Search만으로 충분하고, Entity 간 관계 자체가 중요하거나 여러 단계 탐색이 필요하거나 같은 데이터를 다양한 관계 관점에서 봐야 하거나 답변의 연결 근거를 제공해야 할 때 도입을 고려하라고 정리합니다. Graph DB를 도입하면 데이터 모델링과 운영 시스템도 늘어나므로 **"Graph DB를 쓰는 것 자체보다 해결하려는 문제가 Graph 구조에 적합한지를 먼저 판단하는 것이 중요하다"**는 결론입니다.
- 주목할 point: GraphRAG를 "더 좋은 RAG"가 아니라 **"질문 유형이 다를 때 쓰는 다른 도구"**로 규정한 점이 정확합니다. 도입 판단 기준을 도메인이 아니라 질문의 성격(관계 탐색이 필요한가)에 두라는 조언, 그리고 마지막 절을 아예 "항상 정답은 아니다"로 할애해 모델링·운영 비용을 짚은 균형감이 이 글의 미덕입니다. Agent 구조에서 Graph DB를 데이터 저장소가 아니라 호출 가능한 Tool로 재배치한 관점도 실용적입니다. 같은 날 올라온 토스증권 글이 그래프 RAG를 **실제로 운영하며 겪은** 후보 폭증·홉별 가지치기 문제를 다루므로, 이 글로 개념을 잡고 그쪽으로 넘어가면 이론과 현실이 정확히 맞물립니다.

## [전자결재란? 우리 회사에 필요한 이유와 도입 전 체크리스트](https://library.gabia.com/contents/groupware/15335/)

가중치, 종목 중요도로서의 시가총액, 이벤트의 최신성을 보조 신호로 반영했습니다(시가총액과 최신성이 결과를 결정하는 게 아니라 관련성이 비슷한 후보들 사이의 보조 신호). 제품마다 중요하게 보는 관계 흐름이 달라 특정 노드 유형 순서와 일치하는 경로에 가산점을 주는 `path_preference` 파라미터를 만들어, 검색기를 제품별로 따로 만들지 않고도 ## [Cilium, Under the Hood #1: eBPF로 들여다보는 Kubernetes 네트워크의 동작 원리](https://on.com2us.com/tech/cilium-ebpf-under-the-hood-part1/)

- 본문 요약: eBPF 기반 CNI인 Cilium이 Kubernetes 네트워크를 어떻게 처리하는지 실습과 소스코드로 파고드는 시리즈 1편입니다(글머리에 "eBPF나 쿠버네티스 자체의 동작 원리를 설명하는 글이 아니다"라고 못 박습니다). 먼저 세 개념을 구분합니다 — **Identity**(무엇인가/정체, 파드의 쿠버네티스 라벨에서 유도되며 클러스터 Endpoint로 삼는 방식으로 풉니다. 전통적 IPTables는 규칙 체인을 선형 탐색해 대규모에서 병목이 되는 반면 Cilium은 eBPF를 `cgroup/connect`와 TCX 계층에 붙입니다. 실습은 kind로 `disableDefaultCNI: true` 클러스터를 만들고 Cilium 1.19.5를 설치하는 데서 시작해, `cilium status --verbose` 출력의 각 항목(KubeProxyReplacement, Routing: Tunnel[vxlan], Attach Mode: TCX — 커널 6.6+ 새 Attach API, Device Mode: veth, Masquerading: IPTables)을 하나씩 해설합니다. `bpftool net show`로 eBPF 프로그램 부착 지점을 확인하는데 `eth0(cil_from_netdev)`, `cilium_net(cil_to_host)`, `cilium_vxlan(cil_from_overlay / cil_to_overlay)`, `lxcXXXXXX(cil_from_container)` 각각의 역할을 짚고, 송신 datapath(`lxc(cil_from_container)` → 같은 노드면 목적지 lxc, 다른 노드면 `cilium_vxlan(cil_to_overlay)`로 VXLAN 캡슐화 → `eth0`)와 수신 datapath(`eth0(cil_from_netdev)` → `cilium_vxlan(cil_from_overlay, 디캡슐)` → 목적지 lxc)를 정리합니다. **eBPF 맵**은 프로그램이 상태를 직접 저장하지 않고 커널 자료구조를 읽고 쓰는 구조로, `cilium_ipcache`(모든 IP → Identity 매핑), `cilium_lb4_services`(서비스 LB 테이블), `cilium_lb4_backends`(백엔드 LB 테이블), `cilium_ct4`(커넥션 트랙)를 `cilium bpf ... list`로 직접 조회합니다. 서로 다른 노드의 netshoot 파드 두 개가 Identity 15160을 공유하는 것을 맵에서 확인하고, `cilium monitor --related-to`로 ping 이벤트의 `identity 15160->15160`, `state new`, `ifindex`를 읽으며, tcpdump로 VXLAN 패킷(바깥 헤더 172.18.0.3→172.18.0.4, 안쪽 10.244.1.182→10.244.2.42)을 실제로 캡처해 바깥 IP 헤더 20B + UDP 8B + VXLAN 헤더 8B 구조를 확인합니다. **IPAM**은 Cluster Scope(Cilium Operator가 CiliumNode 리소스로 노드별 PodCIDR 관리), Kubernetes Host Scope(kube-controller-manager의 `--allocate-node-cidrs`로 정해진 `.spec.PodCIDR`을 cilium-agent가 읽어 사용), Multi-Pool(워크로드 주석·노드 레이블로 여러 풀에서 할당) 세 모드를 구조도와 함께 비교하고, 모드 전환은 마이그레이션보다 클러스터 재생성이 권장된다는 점, `cluster-pool-ipv4-mask-size` 기본값 24가 노드당 254개 파드 IP를 의미한다는 점, multi-pool은 기존 IPTables 방식과 완전 호환되지 않아 eBPF masquerade나 `egressMasqueradeInterfaces` 설정이 필요하다는 점을 짚습니다. **Network Policy** 실습에서는 `CiliumNetworkPolicy`로 ingress를 제한한 뒤 다른 노드에서 ping을 보내 `Policy verdict ... remote ID 64347, ingress, action deny` → `xx drop (Policy denied) to endpoint 162` 로그를 확인하고, `cilium bpf policy get`으로 ingress 허용 목록에 ANY가 없고 `reserved:host`만 있음을 맵 수준에서 확인합니다. 가장 무거운 챕터는 **kube-proxy 대체**입니다. 기존 kube-proxy의 IPTables 체인을 실제 `iptables-save` 출력으로 3단계(KUBE-SERVICES: ClusterIP 패킷을 서비스 체인으로 → KUBE-SVC-XXXX: `-m statistic --mode random --probability`로 백엔드 확률 선택 → KUBE-SEP-XXXX: 실제 파드 IP로 DNAT) 해부하고, statistic 모드는 매 연결마다 독립 랜덤 선택이라 backend affinity가 약한 반면 Cilium의 Maglev는 Consistent hashing Cilium이 이를 푸는 방식은 **Socket-Based Loadbalancing** — 파드 A가 서비스 IP로 `connect`를 호출하면 `cgroup/connect`에 붙은 eBPF가 시스템콜을 가로채 서비스맵·백엔드맵을 조회하고 **소켓에 기록될 목적지를 아예 바꿔치기**해서, 커널이 처음부터 백엔드를 향해 패킷을 생성하므로 별도의 DNAT 과정이 없습니다(UDP는 `recvmsg`/`sendmsg` 후킹). tcpdump로 검증하니 `curl netshoot-svc:80`을 했는데 캡처된 패킷에는 서비스 IP 10.96.57.113이 아예 등장하지 않고 백엔드 IP만 보였습니다. 마지막으로 Cilium 1.19.5 소스코드(`bpf_sock.c`의 `cil_sock4_connect` → `__sock4_xlate_fwd` → `lb4_lookup_service`(`cilium_lb4_services_v2` 맵) → `sock_select_slot % svc->count + 1`로 백엔드 슬롯 선택(`cilium_lb4_backends_v3`) → `sock4_update_revnat`)를 따라가며, RevNAT 맵이 필요한 이유는 `getpeername()`이 "이 소켓은 원래 ClusterIP X로 연결하려 했다"를 되돌려주기 위해서라고 설명합니다. 다음 편에서는 North-South 통신(SNAT vs DSR), Hubble, ClusterMesh 멀티클러스터를 예고합니다.
- 주목할 point: 국내 기술 블로그에서 Cilium을 사용법이 아니라 **eBPF 프로그램 부착 지점 → eBPF 맵 → 커널 소스코드**까지 내려가 파고드는 글은 드물어, Kubernetes 네트워크 내부를 이해하려는 인프라 엔지니어에게는 우선순위가 높습니다. 특히 값진 대목은 세 가지입니다. ①Identity/Endpoint/IP 삼분법 — "정책의 표현은 Identity, 적용 대상은 Endpoint"라는 한 줄로 Cilium의 설계 철학이 정리됩니다. ②kube-proxy의 IPTables 3단계 체인을 실제 출력으로 해부한 뒤 Socket LB와 대조한 구성 — `connect` 시스템콜 단계에서 목적지를 바꿔치기하므로 **DNAT 자체가 없다**는 점, 그래서 tcpdump에 서비스 IP가 아예 안 잡힌다는 검증이 특히 명쾌합니다. ③이론 → 실습(kind + cilium monitor + tcpdump) → 소스코드 순으로 같은 사실을 세 번 확인하는 전개 방식. `-m statistic` 랜덤 선택 vs Maglev consistent hashing의 backend affinity 차이도 실무에서 세션 유지 문제를 겪어본 사람이라면 반가운 대목입니다.

- 회사: 한글과컴퓨터
- 본문 요약: Unity + WebGL로 운영 중인 한컴타자 '필사' 서비스를 React/Next로 마이그레이션하면서, C#/Unity 경험이 없는 프론트엔드 개발자가 겪은 문제를 AI로 푼 기록입니다. 어려움은 둘이었습니다 — 원본 코드를 온전히 이해할 수 없었고, "그대로 옮길 것"(진행률·정확도·완독 처리는 기존과 계산 규칙·저장 규격이 동일해야 함)과 "새로 만들 것"(스크롤 전환·모바일 대응)이 섞여 있었습니다. 그래서 "AI야 코드 짜줘"로 될 일이 아니라, 읽지 못하는 원본을 이해하고 → 뭘 유지·변경할지 판단하고 → 그대로 구현됐는지 검증하는 흐름 전체가 문제였습니다. **핵심 발상은 검증 지점을 코드에서 명세로 옮긴 것**입니다 — C#은 검증할 수 없지만 "이 명세가 내가 만들 서비스의 동작을 맞게 서술했나"는 판단할 수 있고, 이 명세는 구현·검증·리뷰가 모두 참조하는 단일 기준이 되어 **"AI 결과물을 믿을지 말지의 문제"를 "기준에 맞는지의 문제"로 바꿉니다**. 부수 효과로 대화가 길어져 맥락이 날아가거나 새 세션·다른 에이전트가 붙어도 스펙 하나만 건네면 되고, 세션 시작마다 도는 훅이 현재 브랜치·작성된 스펙 목록·진행 중인 스펙을 먼저 띄워 "어디까지 했는지"를 다시 설명하지 않아도 됩니다. 이를 반복 가능하게 만드는 것이 **하네스 엔지니어링**(더 좋은 프롬프트를 찾는 게 아니라 모델이 일하는 환경 — 맥락·도구·절차·안전장치 — 을 설계하는 것)입니다. 명세 추출은 `/extract-spec <unity 파일들>` 커맨드로 고정되며, 전용 에이전트(`unity-spec-extractor`)에 Unity 개념을 React/Next 관점으로 옮기는 변환 규칙과 "클래스/메서드 이름을 명세에 쓰지 말고 사용자 관점 동작으로만 서술하라"는 규칙을 박았습니다. 명세를 **구현이 아니라 '관측 가능한 동작'으로만** 기술하게 한 덕에 ①Unity 내부를 몰라도 검수 가능하고 ②구현 스택이 바뀌어도 그대로 유효합니다. 함정도 있었는데, 전체화면·클립보드·파일 저장 같은 동작은 C#이 아니라 빌드에 얹히는 JS 레이어(jslib + 템플릿 html)에 위임돼 있고 C#에는 `[DllImport("__Internal")]` extern 선언만 보여, 번역 에이전트에 "extern 선언을 만나면 매핑된 jslib·호스트 JS 구현까지 따라가라"는 규칙을 추가했습니다 — **번역이 닿지 못하는 경계를 짚어 보강하는 건 사람의 몫**이었습니다. **한글 IME 사례**가 이 글의 백미입니다. AI에게 초안을 맡기니 웹에서 가장 흔한 composition 이벤트 방식으로 짜줬고 데스크탑 Chrome·Safari에서는 잘 동작했지만, iOS Safari 실기기에서 한글이 자모 단위로 쪼개졌습니다. 원인은 iOS Safari가 (현재 기준) 한글 입력에서 composition 이벤트를 발생시키지 않는 것으로, 일본어·중국어는 정상 동작하는 한글 특정 이슈이며 iOS는 Chrome·Firefox도 WebKit이라 전 브라우저 공통이고, `input` 이벤트의 `isComposing`도 내내 false라 "조합 중이면 건너뛰자"는 차선책조차 통하지 않습니다. 게다가 Playwright 합성 이벤트로는 재현되지 않아(실제 OS IME를 거치지 않으므로) 데스크탑에서도 멀쩡하고 e2e로도 안 잡히는 문제였습니다. 해결은 이벤트 대신 **값 변화**를 보는 것 — hidden textarea를 비우지 않고 직전 값과 현재 값의 공통 prefix를 구해 diff만 추리고, 마지막 글자는 "조합 중일 수 있다"고 보고 판정을 보류했다가 다음 글자가 붙어 확정되면 반영합니다. 이렇게 데스크탑과 iOS가 하나의 입력 경로로 합쳐졌습니다. **page → scroll 전환**에서는 AI를 "가설을 싸게 만들고 빠르게 버리는" 도구로 썼습니다. 후보 ①chunk windowing은 탈락 — 조합 중인 글자가 매 키 입력마다 바뀌는데 그 글자가 큰 덩어리 안에 있으면 브라우저가 덩어리 전체를 reflow하고, 한글은 ㅎ→하→한으로 같은 자리를 여러 번 다시 그리므로 영문보다 이 반복 reflow에 훨씬 민감합니다. 후보 ②가상 페이징(1,500자 페이지)은 성능은 충분했지만 한 페이지에 여러 단락이 뭉쳐 "이 단락만 골라 필사"(1차 출시 범위)를 얹기 어려워 탈락. 후보 ③**단락 단위 가상 스크롤**을 채택 — 보이는 단락 ±버퍼 3개만 실제 글자로 그리고 나머지는 높이만 추정한 placeholder로 두며, 조합 중 글자가 속한 컨테이너가 항상 작아 reflow 범위가 작고 단락 자체가 선택 단위라 부분 필사도 자연스럽습니다(placeholder 높이는 글자 수 휴리스틱으로 추정 후 mount 시 측정값으로 보정해 스크롤 점프 방지, 전환 비용과 입력 지연을 모두 한 프레임 ~16ms 안에). **안전장치**는 부탁이 아니라 자동 차단입니다 — ①원본 Unity 디렉터리 쓰기를 hook이 도구 호출 단계에서 `exit 2`로 차단 ②비밀키를 다루는 서버 전용 코드는 전용 디렉터리 + server-only import를 강제해 클라이언트 번들 유출을 생성 단계에서 차단 ③**검증 담당 에이전트에는 파일 수정 도구를 아예 주지 않아** "검증한다며 코드를 고쳐 버리는" 사고를 구조적으로 불가능하게 만들었습니다. 리뷰는 `code-reviewer` 에이전트가 6개 도메인(보안·데이터·React·일관성·브라우저·성능)으로 쪼개 병렬 점검하되 **리포트만 하고 코드는 고치지 않으며**, "우연히 동작하는 결합, 취약한 문자열 파싱, 기준이 다른 두 위치 값(챕터 전체 기준 offset vs 단락 내부 기준 offset)을 섞어 쓰는 실수" 같은 것을 집중적으로 찾게 했습니다. 마지막으로 계획→구현→검증→배포 완전 자동화 흐름은 대부분 갖췄지만 **자율성은 의도적으로 제한**했다고 밝히며, 마이그레이션에서 정확성은 속도보다 중요하므로 이는 손해가 아니라 의도된 트레이드오프라고 정리합니다.
- 주목할 point: "모르는 기술 스택을 AI로 옮긴다"는 자극적인 전제를 실제로 성립시킨 장치가 **명세**라는 점이 핵심입니다. 코드→코드가 아니라 코드→명세→코드로 한 단계를 거치면 검증 기준이 생기고, 그 기준이 있어야 AI 산출물을 판별할 수 있습니다. 실무에 그대로 옮길 만한 것도 많습니다 — 명세를 구현 디테일이 아니라 관측 가능한 동작으로 쓰게 하면 스택이 바뀌어도 유효하다는 점, 위험 작업을 "하지 마"라는 부탁이 아니라 hook과 권한 분리로 차단한다는 점, 특히 **검증 에이전트에게 수정 권한을 주지 않는** 역할 분리는 즉시 적용 가능합니다. iOS Safari 한글 IME 사례는 그 자체로도 값진 버그 리포트인데(composition 이벤트 미발생 + `isComposing` false + Playwright 재현 불가), **"AI는 가장 흔한 정답을 빠르게 주지만 내 케이스가 그 흔한 정답에 해당하는지는 판단해주지 않는다"**는 교훈의 완벽한 예시입니다. 결론 네 줄("AI를 생성기로만 보지 마라 — 읽기 쪽이 더 강할 때가 많다" 등)은 따로 메모해둘 만합니다.

## [[케클러 인터뷰 시리즈] #5 - AI가 클라우드를 운영하려면, 데이터부터 이해해야 합니다](https://tech.ktcloud.com/entry/2026-08-ktcloud-observability-platform)
- 회사: KT 클라우드
- 본문 요약: kt cloud Data플랫폼팀 김종민 팀장 인터뷰로, Observability를 기반으로 AI가 활용할 수 있는 클라우드 운영 데이터를 만드는 이야기입니다. **Part 1**은 모니터링과 Observability의 차이에서 시작합니다 — 모니터링은 CPU·메모리·디스크처럼 미리 정의한 지표를 감시하는 방식으로 감시 대상이 고정되고 구조가 단순할 때 통했지만, Cloud Native에서는 컨테이너가 수시로 생성·소멸하고 하나의 요청이 여러 마이크로서비스를 거쳐 **문제가 나타난 지점과 실제 원인이 있는 지점이 다릅니다**. 응답 지연 알람이 떠도 인프라 지표는 정상이고 애플리케이션 로그에서도 오류가 안 보이면, 운영자는 여러 대시보드를 오가며 데이터를 찾고 연결하는 데 원인 분석만큼의 시간을 쓰고 어느 시스템을 볼지는 담당자 경험에 의존하게 됩니다. **"모니터링이 이미 알고 있는 문제를 감시하는 방식이라면, Observability는 예상하지 못한 문제가 발생했을 때도 남아 있는 데이터로 원인을 추적할 수 있는 상태를 만드는 것"**입니다. **Part 2**는 Metric(무엇이 언제부터 이상해졌는지)·Log(그 시점에 무슨 일이 있었는지)·Trace(어느 구간에서 지연·실패했는지)를 OpenTelemetry를 표준 수집 규격으로 삼아 하나의 흐름으로 연결한 이야기입니다. 수집 범위를 애플리케이션에 한정하지 않고 네트워크·인프라·플랫폼까지 넓힌 이유는 실제 원인이 하위 계층에 있으면 애플리케이션 데이터만으로는 찾을 수 없기 때문입니다. 중요하게 본 기준은 **연결성·일관성·규모**(서비스·자원·리전·테넌트 레이블과 데이터 규격을 일관되게 관리)이며, 특히 AI가 데이터를 활용하려면 "이 데이터가 어떤 서비스와 자원에 속하며 무엇을 의미하는지"가 데이터 안에 명시돼 있어야 한다고 강조합니다 — 사람은 여러 화면과 경험으로 맥락을 추론하지만 AI는 그 관계가 데이터로 표현돼 있어야 하기 때문입니다. **Part 3**은 AI Agent를 각 운영 시스템에 직접 연결하면 연결 구조가 복잡해지고 인증·권한도 시스템별로 관리해야 하므로 **MCP Hub**라는 공통 연결 계층을 둔 이야기입니다. 핵심은 **AI가 데이터 저장소에 직접 접근하지 않는다**는 것 — MCP Hub에 '특정 기간의 지표 조회', '특정 자원의 상태 확인'처럼 목적이 정의된 도구를 등록하고 Agent가 필요한 도구를 선택해 호출합니다. 도구 정의 단위도 설계 요소인데 범위가 너무 넓으면 AI가 적절한 도구를 못 고르고 너무 세분화하면 질문 하나에 불필요하게 많은 호출이 필요해, **운영자가 실제로 질문하는 단위**를 기준으로 설계했습니다. **Part 4**는 AI 데이터 접근 통제를 세 질문(누가 요청했는가 / 무엇까지 볼 수 있는가 / 요청은 어떻게 처리됐는가)으로 정리합니다. AI Agent가 자체 권한으로 조회하는 게 아니라 **요청한 사용자의 신원을 각 시스템까지 전달하고 최종 접근 여부는 각 시스템의 기존 권한 정책이 판단**하는 구조여서, AI가 연결돼도 기존 보안 원칙과 데이터 접근 경계가 유지됩니다. AI의 활동 역시 Observability의 대상이라 어떤 사용자가 어떤 도구를 호출했고 어떤 정보가 오갔는지 기록하며, 외부로 나가면 안 되는 정보나 **AI의 동작에 영향을 줄 수 있는 외부 지시**가 포함됐는지도 확인하고 이 기록을 다시 Observability Platform에 적재합니다. **Part 5**는 상용 대신 Grafana LGTM + OpenTelemetry OSS를 택한 이유(비용뿐 아니라 기술을 직접 통제할 수 있는 구조 — Observability가 내부 도구이면서 동시에 고객 제공 서비스이므로 CSP 환경에 맞게 확장·연결 가능해야 함)와, 대규모 CSP에 필요한 멀티테넌시·권한 관리·확장성을 위해 **Telemetry Gateway**(고객별 데이터를 테넌트 단위로 격리하고 클러스터로 분산)와 **Siren**(알람·레이블·대시보드 연결 규격 표준화)을 직접 개발한 이야기입니다. 원칙은 **오픈소스 소스코드 자체를 수정하지 않는 것** — 필요한 기능은 독립 컴포넌트로 구현해 오픈소스의 발전을 그대로 따라가면서도 kt cloud의 속도로 개발할 수 있게 했고, 이를 "내재화가 부채가 아니라 자산이 되게 만드는 구조"라고 표현합니다. **Part 6**은 고객 데이터와 내부 운영 데이터를 하나의 저장소에 두고 권한으로만 구분하면 **설정 오류가 곧 데이터 노출**이 되므로 **서로 다른 클러스터에 저장해 저장 계층부터 경계를 분리**한 이야기입니다(고객 데이터 클러스터 안에서도 Telemetry Gateway가 프로젝트를 테넌트로 매핑해 격리). 사후에 접근 기록을 확인하는 것보다 애초에 서로 닿을 수 없는 구조를 만드는 접근이며, 공공 부문 클라우드 인증 요건까지 고려해 설계 단계에 반영했습니다. **Part 7**은 "왜 자원이 늘었는가", "어떤 고객과 서비스에 영향을 주는가", "현재 사용량이 비용 측면에서 어떤 의미인가"처럼 Metric·Log·Trace만으로는 답하기 어려운 질문을 위해 클라우드 자원·고객·비용·매출까지 연결하는 통합 데이터 플랫폼으로 범위를 넓히고 있다는 계획이며, 장애 시 AI가 구간을 좁히고 영향 범위를 정리하고 과거 유사 장애 이력까지 연결하면 운영자는 **'어디를 볼 것인가'보다 '무엇을 할 것인가'를 판단하는 데 집중**할 수 있다고 정리합니다.
- 주목할 point: **"AI에게 운영을 맡기려면 먼저 데이터가 연결돼 있어야 한다"**는 순서 정리가 이 글의 축입니다. 특히 MCP Hub를 단순 도구 연결 지점이 아니라 인증·인가와 감사 이력의 지점으로 설계하고, **Agent 자체 권한이 아니라 요청 사용자의 신원을 각 시스템까지 전달해 기존 권한 정책이 판단하게 한** 구조는 같은 날 밸런스히어로가 제시한 Governance·Interface 논의와 정확히 겹칩니다(두 글을 나란히 읽으면 같은 문제에 대한 두 조직의 답을 비교할 수 있습니다). 실무적으로 인상적인 것은 셋 — MCP 도구를 "운영자가 실제로 질문하는 단위"로 정의했다는 설계 기준, 오픈소스를 포크하지 않고 독립 컴포넌트로만 보완해 업스트림을 따라가는 원칙, 그리고 권한이 아니라 **저장 계층부터 클러스터를 나눠** 설정 오류가 노출로 이어지지 않게 한 격리 방식입니다. AI의 활동 자체를 관측 대상으로 삼고 프롬프트 인젝션성 외부 지시까지 확인한다는 대목도 눈여겨볼 만합니다.
