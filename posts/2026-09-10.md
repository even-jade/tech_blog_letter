- 주목할 point: 정밀도는 "최대 처리량"이 아니라 "SLO 하 처리량"으로 골라야 한다는 기준 전환, 그리고 대화형 풀과 배치 풀을 나눠 speculative decoding·priority 스케줄링을 배치 쪽에만 적용하는 운영 설계가 핵심입니다. 서버 플래그보다 prefix cache 적중률이 처리량을 정한다는 실측은 시스템 프롬프트 공통화 같은 프롬프트 설계가 곧 인프라 비용이라는 점을 보여줍니다.

## [조건부 호출로 줄인 API 비용](https://www.nextree.io/jogeonbu-hoculro-julin-api-biyong/)
- 회사: 넥스트리
- 본문 요약: 마이데이터 서비스에서 지난 글의 응답 지연(SWR 패턴으로 해결)에 이어 마주친 비용 문제를 다룹니다. 외부 금융기관 조회 API가 호출 건수 기반 과금으로 전환되면서, 갱신 때마다 기관 목록→계좌 목록→계좌 상세→거래 내역을 변경 여부와 무관하게 연쇄 호출하던 구조가 그대로 운영 비용이 됐습니다. 해결은 조회 Timestamp 기반 조건부 호출과 호출 시점 재배치입니다. 이전 조회 시점 이후 변경이 있는지 가벼운 확인 호출로 먼저 검사하고 변경이 있을 때만 상세를 조회하며, 주기 기반 배치 갱신으로 호출 시점을 모으고, 계좌 거래 내역 같은 무거운 상세 데이터는 사용자가 필요로 할 때 Lazy Loading으로 분리했습니다. 지나고 보니 이는 HTTP가 오래전부터 표준으로 제공한 조건부 요청(If-Modified-Since/ETag)과 같은 발상이었고, SWR이 "오래된 데이터라도 먼저 주고 검증은 나중에"로 응답 속도를 아끼는 반면 조건부 요청은 "검증부터 하고 안 바뀌었으면 전송하지 않는다"로 호출·전송 비용을 아끼는, 같은 캐싱 이론 아래 반대 방향의 전략이 화면 응답과 외부 호출이라는 다른 지점에 공존했다고 정리합니다. 외부 기관의 Timestamp 정확도·스펙 준수 편차와 데이터 최신성 지연의 허용 범위는 계속 조율해야 하는 트레이드오프로 남았습니다.
- 주목할 point: 실무에서 찾은 해법을 HTTP 조건부 요청이라는 표준 메커니즘으로 재해석해 SWR과 대비시킨 점이 핵심입니다. "무엇을 아낄 것인가"(사용자 대기 시간 vs 호출·전송량)에 따라 같은 서비스 안에서도 다른 캐싱 전략을 지점별로 골라야 한다는 프레임은 외부 API 과금이 있는 어떤 서비스에도 적용할 수 있습니다.
