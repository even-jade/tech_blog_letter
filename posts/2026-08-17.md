## [VLM을 이용한 시각적 문서 검색: ColPali와 ColQwen](https://devocean.sk.com/blog/techBoardDetail.do?ID=168438&boardType=techBlog&isShared=Y)
- 회사: SK DEVOCEAN (SK AX)
- 본문 요약: 문서를 텍스트로 변환한 뒤 검색하는 기존 파이프라인이 OCR 오류·레이아웃 분석 불일치·캡셔닝 왜곡을 단계마다 누적시키고, 무엇보다 취소선이나 표의 행/열 배치처럼 시각적 구조로만 표현되는 정보를 복원하지 못한다는 문제에서 출발합니다. 대안으로 페이지 이미지 자체를 VLM으로 임베딩하는 시각적 문서 검색을 소개하며, 단일 벡터 Bi-Encoder(BiPali)와 Late Interaction 기반 Multi-Vector(ColPali)의 차이를 ViDoRe 벤치마크 수치(BiPali 58.8 → ColPali 81.3 nDCG@5)로 보여줍니다. 이어 T월드 이벤트 배너 데이터로 ColQwen2-v1.0 + Qdrant(MAX_SIM comparator) 기반 Baseline을 구성한 과정을 코드와 함께 정리했습니다. "크리스마스때 갈만한 겨울 이벤트" 질의에 배너 문구에 없는 단어임에도 산타 복장·눈 내리는 밤하늘 같은 시각 요소만으로 관련 배너를 찾아냈습니다.
- 주목할 point: Baseline 구성 이후 마주친 실전 문제와 해법이 이 글의 알맹이입니다. (1) ColQwen2의 visual token 수는 이미지 면적에 비례하고 768개로 제한되므로, 840×9,610px 배너는 폭 224px까지 약 3.8배 축소되어 할인율 배지조차 판독 불가가 됩니다. 토큰 제한을 늘리는 대신 chunk 분할이 효과적이라는 결론(chunk마다 제한이 새로 적용됨)과, 경계에 걸친 배지·문구 손실을 막는 오버랩 설정이 실용적입니다. (2) 청킹 후 같은 배너의 여러 chunk가 상위를 점령하는 문제는 field collapsing(Qdrant Grouping API)으로 묶되, 여러 chunk 동시 매칭 자체가 유의미한 신호라 나머지를 버리지 않았습니다. (3) MaxSim 점수는 질의 토큰 수에 비례해 커지므로 절대 임계값이 무의미하다는 지적과, 최상위 점수 대비 비율(예: 0.8) + 절대 하한 병용이라는 해법이 바로 쓸 만합니다. 다만 페이지당 257.5KB(텍스트 임베딩은 10KB 이하)라는 인덱스 크기 trade-off도 함께 짚습니다.

## [Amazon Bedrock 기반 사내 LLM, 키 발급부터 비용 차단까지: F&F의 LiteLLM 게이트웨이 운영 사례](https://aws.amazon.com/ko/blogs/tech/fnf-llm-gateway-on-amazon-bedrock/)
- 회사: AWS (F&F)
- 본문 요약: 전사 플랫폼을 하향식으로 기획하는 대신 사내에서 AI를 가장 많이 쓰는 팀이 자기 팀용으로 먼저 만들고 검증한 사례입니다. 최상위 모델을 이틀 시험 사용했다가 기존 대비 몇 배 비용이 청구된 사건이 직접적 계기였습니다. Amazon Bedrock만으로는 "알람은 되지만 차단은 안 되고"(AWS Budgets는 임계 알림만), Service Quotas는 계정·리전 단위라 사용자별 배분이 불가하며, Bedrock API 키가 IAM principal 권한을 그대로 상속해 사용자별 모델 세트 관리가 어렵다는 한계를 짚습니다. 그래서 Bedrock이 잘하는 영역(모델 서빙·IAM 인증·로깅)은 그대로 두고, 셀프서비스 발급·모델 승인·예산 차단만 보완하는 구조로 컨트롤플레인(사내 포털 "LLM Lite")과 데이터플레인(EKS 위 LiteLLM proxy)을 나눴습니다. 예산은 사용자/키 단위 일 예산과 프로젝트(LiteLLM team) 단위 월 예산 2계층으로 두고, 초과 시 429(ExceededBudget)로 자동 차단합니다.
- 주목할 point: 귀속 기준을 새로 만들지 않고 기존 SSO 이메일(개인)과 `svc:{서비스명}` 식별자(서비스)를 그대로 재사용해, 개인 실험과 서비스 상시 호출이 섞이지 않게 한 설계가 깔끔합니다. 예산 경고 수신자도 수동 목록이 아니라 Entra 그룹 멤버를 실시간 조회해 담당자 교체에 자동 대응합니다. 운영 교훈 세 가지도 구체적입니다 — Internal ALB로 CIDR 제한을 걸었더니 같은 VPC 내 Pod는 SNAT가 일어나지 않아 Pod IP가 그대로 도달해 차단된 사건, 전환 완료 판정을 200 응답이 아니라 "서비스 로그의 base_url + CloudTrail 직접 호출 부재 + 게이트웨이 로그 정상 기록" 3중 확인으로 바꾼 점, 게이트웨이 경유 후에도 프롬프트 캐시가 유지되는지 먼저 확인하고 옮긴 점입니다.

## [AI Agent를 위한 OpenSearch 검색 품질 평가하기 (Part 1)](https://aws.amazon.com/ko/blogs/tech/evaluate-ai-agent-search-quality-with-amazon-opensearch-service-1/)
- 회사: AWS
- 본문 요약: "검색 품질을 어떻게 측정하고 계신가요"라는 질문에 대부분 "체감상 좋아진 것 같아요"로 답한다는 문제의식에서 시작해, Amazon OpenSearch Service + Bedrock으로 검색 품질을 정량 측정하는 시스템을 구축한 기록입니다. Agent의 검색은 사람의 검색과 달리 쿼리를 Agent가 만들고, 결과를 LLM이 그대로 읽으며, 검색이 답변의 상한을 정한다는 점을 먼저 정리합니다. 그 다음 LLM-as-a-Judge 채점기를 Gold Qrels와 대조해 검증(SciFact 65%, MIRACL 75% 일치, MIRACL Spearman 0.94)한 뒤, BM25 / 시멘틱(k-NN, Cohere Embed Multilingual v3) / 하이브리드(RRF)를 BEIR 4개 데이터셋에서 비교합니다. SciFact·TREC-COVID는 시멘틱이, NFCorpus·Touche-2020은 하이브리드가 1위였습니다.
- 주목할 point: 함정 세 개가 이 글의 핵심입니다. (1) SciFact에서 Cohen's Kappa가 0.0, Spearman이 NaN으로 나온 건 채점기가 나빠서가 아니라 Gold Qrels에 긍정 레이블만 있어 분산이 없었기 때문 — 검증 데이터에는 반드시 부정 샘플도 넣어야 한다는 교훈. (2) TREC-COVID는 k-NN의 NDCG@10이 0.789로 최고인데 Recall@10은 0.020(2%)입니다. 쿼리당 정답이 수백 개라 상위 10개로는 구조적으로 담을 수 없기 때문인데, RAG에 그대로 쓰면 LLM이 정답의 98%를 보지도 못합니다. 지표 하나로는 검색 품질을 말할 수 없습니다. (3) 한국어 BM25가 0.017로 낮았던 원인은 데이터가 아니라 형태소 분석기였습니다 — standard analyzer가 "전자담배는"을 한 토큰으로 잡아버려서, Nori 적용 후 0.032로 +87% 상승(k-NN은 0.044로 변화 없음). 또 Touche-2020처럼 티켓 번호·에러 코드 같은 정확한 식별자가 쟁점인 데이터에서는 시멘틱이 오히려 독이 될 수 있다는 지적도 Agent 설계에 바로 적용됩니다.
