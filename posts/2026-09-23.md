## [LLM 하나만 믿지 마세요 — 모든 LLM을 관점별로 싸우게 한 코드리뷰, Code Review War](https://techblog.samsung.com/blog/article/98)
- 회사: 삼성전자
- 본문 요약: 같은 PR을 어떤 LLM에 어떤 프롬프트로 맡기느냐에 따라 결함이 잡히기도 하고 묻히기도 하는 현상에서 출발해, 사용 가능한 모든 LLM을 워커로 동원하는 Code Review War(CRW)를 만든 기록입니다. 처음 설계는 LLM들의 경쟁이었지만, 운영해 보니 승패보다 "보안 관점은 누가 봤는가, 동시성 관점은 비어 있지 않은가"가 품질을 갈랐기에 페르소나(리뷰 관점)를 1급 실행 단위인 '레인'으로 격상하고 LLM을 그 레인에 배치되는 워커로 바꿨습니다. 예선(qualify)에서 각 모델의 지연·동시성·컨텍스트 창을 수집해 로스터를 확정하고, 8개 관점(소비자 크리티컬, 런타임 크래시, 호환성, 의도 정합, 옵션 분기, 보안, 동시성·리소스, 관점 지시를 일부러 얹지 않는 free-scope) 레인에 워커를 배치해 diff를 청크로 잘라 병렬 리뷰합니다. 살아있는 모델 수가 매번 다르므로 레인 배치는 워커 수에 따른 정책(1개=통합 겸직 / 2~6개=우선순위 분할 / 7개=1:1 전담 / 8개 이상=상위 레인 2중화)이고, 워커가 죽으면 다른 워커가 넘겨받는 '레인 스틸'로 레인이 비지 않게 했습니다. 워커의 출력은 ① 리뷰에 참여하지 않은 심판 모델이 파일 실재·근거 인용·오탐 여부를 검증하고 ② LLM 없이 파일 경로 정규화와 안정 키로 중복을 묶는 결정적 병합(결과 도착 순서가 달라도 같은 리포트) ③ 발견 사항 간 연관을 규칙으로 묶고 심판 모델을 한 번 호출해 "얽히면 어떤 사고가 되는가"를 서술하는 시너지 종합을 거칩니다. LLM에는 승인/차단 권한을 주지 않고, 게시는 코멘트 이벤트와 AI 라벨로만 사람이 고른 발견에 대해서 이뤄집니다. 품질은 감이 아니라 숫자로 정했습니다 — 결함을 매설한 샘플 PR 6종(Python·Java·TypeScript·C 임베디드)과 정답지를 만들고 자동 채점(Critical 5·High 4·Medium 3·Low 1점, 정답지 외 지적은 건당 1점 감점)하되 정답지는 채점 단계에서만 열어 리뷰 프롬프트로 새지 않게 격리했습니다. 단일 모델 8관점 한 프롬프트(40/74점, 결함 12/22)에서 3모델 × 8관점 완전 중첩(56/74점, 결함 17/22, Critical/High 13/16)으로 바꾸자 프롬프트는 그대로인데 점수가 40% 올랐고, 8모델 1:1 배정은 탐지 수는 같지만 오탐 9건·호출 24회로 효율이 낮아 순환 진단용으로만 남겼습니다.

## [연 300시간을 아낀 AI 상담 서비스](https://toss.tech/article/AI_chatbot)
- 회사: 토스(토스뱅크)
- 본문 요약: 전세대출 팀에서 AI 상담 서비스를 디자인한 과정입니다. 상담팀에서 "사용자들이 서류를 제대로 제출하지 못해 심사가 자꾸 막힌다"는 이야기를 듣고 문의 데이터를 직접 열어보니, 서류 제출 방법뿐 아니라 단순 정보를 묻는 문의량이 유독 높았고 이런 문의가 상담 인력을 붙잡아 정작 심사가 늦어지고 있었습니다. 그런데 그 정보는 이미 화면에 쉽게 설명되어 있었습니다. 문제는 사용자가 답을 못 찾는 게 아니라, 화면에서 정보를 찾고 필요한 내용을 골라내고 그 답이 정말 내 상황에 맞는지 판단하는 것까지 모두 사용자 몫이었다는 점입니다. 집을 구하는 큰돈이 걸린 전세대출에서는 조금이라도 확실하지 않으면 '아마 맞겠지' 하고 넘어가기 어려워 결국 사람에게 확인하고 싶어집니다. 그래서 화면이 먼저 설명하는 방식에서, 사용자가 자기 말로 묻고 제품이 답하는 방식으로 방향을 바꿨습니다. 같은 궁금증도 "태아도 자녀로 쳐요?" "임신 중인데 부양가족에 들어가나요?"처럼 표현이 제각각이고 보증금 규모·계약 형태·신청 시점에 따라 답도 달라지므로 AI가 필요했고, 디자이너·대출 운영팀·머신러닝 팀 세 팀이 모여 만들었습니다. 그런데 출시 후 상품 인트로에 "대출 신청하기 전, 궁금한 점 AI에게 물어보기" 배너로 진입점을 놓고 누르면 빈 입력창이 열리는 구조로 했더니 거의 아무도 누르지 않았습니다. 상담 전화가 줄어드는 경향은 보였지만 쓰는 사람 자체가 너무 적어 효과를 확인할 수조차 없었습니다. 원인을 "무엇을 물어야 할지 몰라서"로 보고 — 빈 입력창은 무엇이든 물어볼 수 있지만 어떤 질문부터 할지는 사용자가 정해야 하고, AI가 어디까지 답하는지도 알기 어려움 — 상담 문의 데이터를 다시 살펴 각 단계에서 가장 많이 물었던 질문을 진입점에 노출했습니다(인트로: 금리·한도, 법인 임대인 대출 가능 여부 / 심사 대기: 심사 종료 시점, 결과 발표 시점). 그 결과 인트로 화면 AI 사용률 약 5배, 심사 대기 화면 약 2배가 올랐고, 사용자들이 자기 상황을 덧붙여 자유롭게 질문하기 시작했습니다. AI에 질문해 적합한 답변을 받은 사용자는 상담 전화로 이어지는 비율이 약 10%p 낮았고, 상담 전화는 월 550건 줄어 통화 시간으로 환산하면 연 300시간입니다.
- 주목할 point: "답을 보여주는 것과 확신을 주는 건 다른 일"이라는 결론이 핵심입니다. 화면에 필요한 정보가 이미 있어도 사용자는 그 정보가 자기 상황에 적용되는지 확신할 수 없어 전화를 걸었고, 그래서 화면 설계는 '무엇을 알려줘야 하지?'에서 끝나면 안 되고 지금 이 사용자가 무엇을 걱정하고 무엇을 확신하지 못하는지까지 봐야 한다는 것입니다. 마지막 '적용해보기' 두 가지도 바로 쓸 만합니다 — ① 화면 밖에 쌓인 신호 찾아보기(지표 안에서는 잘 넘어간 것처럼 보여도 고객센터 문의나 다른 팀이 대신 받고 있는 일 안에 화면이 못 풀어준 문제가 남아 있을 수 있음) ② 근본적인 구조 의심하기(더 잘 보이게 하고 문구를 다듬고 자리를 옮겨도 안 풀린다면 손봐야 할 건 화면이 아니라 그 화면이 작동하는 방식). 진입점에 남들이 실제로 물어본 질문을 보여주는 것만으로 사용률이 5배 올랐다는 결과는 AI 기능의 발견 가능성 문제를 다루는 팀에 직접적인 레퍼런스입니다.

## [루프 엔지니어링 실전: Claude Code /goal 분석과 Stop 훅 재구현](https://insight.infograb.net/blog/2026/09/23/loop-engineering/)
- 회사: 인포그랩
- 본문 요약: 에이전트가 '작업을 완료했다'며 멈췄지만 확인해 보면 테스트가 여전히 실패하는 상황 — 이름은 자동화지만 사람이 여전히 루프 한가운데서 프롬프트를 입력하고 결과를 확인하는 문제에서 출발합니다. 원인은 단순합니다. 에이전트의 턴은 실제 작업 완료 여부와 무관하게 에이전트가 스스로 '끝났다'고 판단하는 순간 끝나며, 그 판단이 맞는지 밖에서 확인하는 단계도 틀렸을 때 사람 없이 다음 턴을 이어가게 하는 장치도 기본 동작에 없습니다. 루프 엔지니어링은 언제 시작할지(트리거), 끝났다는 걸 무엇으로 판정할지(완료 판정), 언제 멈출지(정지 조건)를 사람 대신 시스템이 맡도록 설계하는 일입니다. 2026년 6월 Addy Osmani(당시 Google Cloud AI 디렉터, 현재 Anthropic에서 Claude Code 개발 참여)가 에세이 'Loop Engineering'에서 "에이전트에 프롬프트를 입력하는 사람인 당신 자신을 대체하는 일"로 정리하며 널리 쓰이기 시작했고, 1년 전만 해도 bash 스크립트로 직접 만들어야 했던 구성 요소(스케줄 실행, 워크트리, 스킬, 플러그인·커넥터, 서브에이전트)가 지금은 제품 기능으로 지원됩니다. Claude Code 팀 분류에 따라 네 가지 루프를 정리합니다 — 턴형(사용자 프롬프트 하나로 시작해 한 턴 안에서 컨텍스트 수집·작업·확인을 반복; 사람이 하던 검증 절차를 SKILL.md에 적어두면 E2E 자체 검사 범위를 넓힐 수 있고, UI 변경이라면 편집 성공으로 끝내지 말고 개발 서버를 띄워 브라우저로 조작하고 전후 스크린샷을 남기고 콘솔 오류를 확인하고 Chrome DevTools MCP로 Core Web Vitals까지 점검), 목표형(/goal — 완료 조건을 정해두면 충족할 때까지 턴을 이어가고, 멈추려 할 때마다 평가 모델이 조건 충족 여부를 판정해 미충족이면 다시 작업시킴; 단 평가 모델은 명령 실행이나 파일 읽기 없이 대화에 드러난 내용만 보므로 테스트 통과 수나 점수처럼 출력으로 확인 가능한 결정적 지표를 기준으로 둬야 효과적), 시간형(/loop, /schedule — 간격을 지정하면 사용자가 취소하거나 7일 만료까지 계속 실행되고 간격을 생략하면 Claude가 1분~1시간 사이로 정하며 작업이 끝나면 스스로 종료 가능; /loop는 로컬 세션에 묶이고 /schedule 루틴은 클라우드에서 돌지만 리서치 프리뷰이며 최소 간격 1시간), 주도적(이벤트·일정 트리거에 auto mode와 동적 워크플로를 조합). 이후 /goal의 동작을 Stop 훅 기반으로 해석하고 커스텀 훅으로 유사 기능을 재구현하는 과정까지 다룹니다.
- 주목할 point: "검사 항목이 정량적일수록 Claude가 스스로 검증하기 쉬워지고 사람이 확인하고 다시 지시하는 횟수도 줄어든다"는 원칙이 이 글 전체를 관통합니다. 특히 목표형 루프의 평가 모델이 대화 내용만 보고 판정한다는 제약을 명시한 부분이 중요한데, 이 때문에 "잘 동작하면 완료" 같은 서술적 조건은 작동하지 않고 테스트 통과 수나 Lighthouse 점수처럼 에이전트 출력에 드러나는 결정적 지표가 필요합니다. 완료 조건과 함께 최대 턴 수(정지 조건)를 반드시 같이 적어 무한 루프를 막고, 예외 종료 경로를 미리 준비하라는 조언도 실전에서 바로 필요한 부분입니다. 프롬프트 엔지니어링(일회성 상호작용)과 루프 엔지니어링(여러 단계·주기 반복 작업)의 적용 지점을 나눈 정리도 자동화 범위를 정할 때 기준이 됩니다.
