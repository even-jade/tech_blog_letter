## [AI 데이터센터 효율 지표 4가지 [PUE·WUE·ERF·REF]](https://library.gabia.com/contents/infrahosting/15611/)
- 회사: 가비아
- 본문 요약: GPU 고밀도 워크로드가 랙당 전력밀도와 냉각 부하를 함께 끌어올리면서 전력만 재는 PUE 하나로는 AI 데이터센터의 효율을 판단하기 어려워졌다는 문제의식에서, ISO/IEC 30134(EN 50600-4) 시리즈로 표준화된 네 지표를 정리한 글입니다. PUE(총 시설 전력 ÷ IT 장비 전력)는 선도 하이퍼스케일이 약 1.1, 업계 평균 1.56, 신축 목표 1.2~1.4이며 독일은 2027년 1.5 이하·2030년 1.3 이하를 요구합니다. WUE(연간 물 사용량 ÷ IT 에너지, L/kWh)는 증발식 냉각 업계 평균 1.8~1.9인 반면 AWS 0.19, Microsoft 0.30~0.49 수준이지만 같은 사업자도 애리조나 1.52 대 싱가포르 0.02처럼 지역 편차가 큽니다. ERF(재사용 에너지 ÷ 총 에너지)는 현실적으로 0~20%에 머물며 지역난방망 존재 여부에 좌우되고, 독일은 2026년 7월부터 신축에 최소 10%를 의무화합니다. REF(재생에너지 ÷ 총 에너지)는 하이퍼스케일러가 연간 100% 매칭을 선언하지만, PPA·인증서로 총량만 맞춘 100%와 시간당 무탄소 매칭(Google 실측 65% 안팎)은 의미가 다릅니다. EU 에너지효율지침(EED 2023/1791) 제12조는 IT 전력 500kW 이상 데이터센터에 네 지표의 연간 보고를 의무화했고, 한국은 강제 체계가 없지만 글로벌 고객·ESG 기준을 따르면 같은 지표로 평가받게 됩니다.
- 주목할 point: 수냉 도입으로 PUE를 낮추면 WUE가 나빠지고, 공랭으로 물을 아끼면 PUE가 나빠지는 식으로 지표끼리 맞바꾸는 관계라는 점이 핵심이며, 단일 수치 대신 네 축의 균형과 해석 방식을 함께 봐야 합니다. 데이터센터 비교나 계약 협상 시 REF는 연간 총량 매칭인지 시간당 매칭인지, 직접 생산인지 인증서 구매인지를 확인하고, WUE는 지역 기후·냉각 방식, ERF는 폐열 수요처 유무까지 같이 검토하라는 적용 포인트가 실용적입니다.

## [NATS JetStream 장애 분석](https://www.nextree.io/nats-jetstream-jangae-bunseog/)

- 주목할 point: Consumer 상태값 6개(Last Delivered, Ack Floor, OutStanding Acks, Unprocessed, Redelivered, Waiting Pulls)를 표로 정리하고 세 가지 케이스별로 어느 값을 보고 어디를 의심할지 짚은 진단 절차가 실무 런북으로 바로 쓸 만합니다. Durable Consumer의 "상태 유지"라는 장점이 비정상 종료 환경에서는 오히려 장애를 이어받는 원인이 된다는 점, 그리고 재시작 시 상태를 초기화하는 쪽으로 운영 정책을 바꾼 판단이 핵심입니다.

## [Main Thread Blocking 개선 사례](https://www.nextree.io/main-thread-blocking-gaeseon-sarye/)
- 회사: 넥스트리
- 본문 요약: 수만 건의 데이터를 페이징 없이 스크롤로 표현하고 수십 개 컬럼에 필터를 걸며 Cell 값에 따라 배경색을 달리 표시해야 하는 AG Grid 화면에서, 데이터 수신 후 가공·표현에 시간이 오래 걸리고 로딩 중 다른 동작을 하면 화면이 멈추던 문제를 개선한 사례입니다. 초기 구현은 Cell 단위 valueGetter에서 Related Data를 filter()로 탐색해 조합하는 구조라 Main Data N건 × Related Data M건의 O(N×M) 탐색이 발생했고, 정렬·필터·갱신 때마다 Cell 값이 재계산되어 같은 연산이 반복됐습니다. 브라우저는 50ms를 넘는 Task를 Long Task로 분류하며 그동안 사용자 입력 처리와 렌더링이 지연되므로, 전체 처리 시간뿐 아니라 Main Thread가 한 번에 수행하는 작업량을 줄이는 관점이 필요했습니다. 개선은 Related Data를 targetId 기준 Map으로 사전 집계해 Lookup 구조를 만들고, Grid에 전달하기 전 Main Data에 relatedNames를 포함시켜 Cell 계산 자체를 제거하는 방식이었습니다. Virtualization은 DOM 범위만 줄일 뿐 데이터 구성·Cell 계산의 JavaScript 비용은 줄이지 못한다는 점도 짚었습니다.
- 주목할 point: "Grid에 데이터가 많다"가 아니라 "각 데이터를 표현하기 위한 탐색과 가공이 반복된다"로 문제를 재정의한 것이 핵심입니다. 반복 탐색은 Lookup 구조로, Cell 단위 가공은 사전 계산으로, 동일 계산 반복은 결과 재사용으로 대응하는 정리표가 명확하고, Web Worker나 Task 분할 같은 복잡한 방법보다 Main Thread에서 무엇이 반복되는지 먼저 확인하라는 우선순위 제안이 실용적입니다.

LLM에게 번역은 특별한 작업이 아니라 "번역해줘: [원문]" 뒤에 이어질 토큰을 예측하는 일상 동작이며, 다국어 텍스트를 학습하면서 언어 간 대응을 암묵적으로 습득한 결과입니다. 파파고 같은 기존 NMT는 인코더·디코더가 분리되고 크로스 어텐션을 쓰는 반면 LLM은 원문과 번역문을 하나의 문맥으로 이어 인과적 셀프 어텐션만으로 처리하는 Decoder-Only 구조라 스케일링과 데이터 확보에 유리합니다. 실무 차이로 NMT는 문장 단위·파인튜닝 필요·Constrained Decoding으로 일관성 강제·~100ms 속도인 반면, LLM은 문서 전체 처리·프롬프트로 즉시 지시 반영·긴 문서에서 일관성이 흔들릴 수 있음·10~100배 느림으로 정리하며, 지연시간이 중요한 환경에서는 여전히 NMT가 쓰인다고 설명합니다. AI 번역은 엄밀히 학습된 패턴 기반의 확률적 추측이며 그 추측이 늘 옳지는 않다는 화두로 2편(오착)을 예고합니다.
- 주목할 point: 번역 실무자의 시각에서 Encoder-Decoder(NMT)와 Decoder-Only(LLM)의 구조 차이가 처리 단위·지시 반영·일관성·속도라는 실무 지표로 어떻게 드러나는지 표로 대비한 부분이 유용합니다. KV 캐시가 있어도 문맥이 길어질수록 지연이 커진다는 설명은 LLM 기반 번역 파이프라인의 속도 병목을 이해하는 데 도움이 되고, 지침·용어집을 컨텍스트로 넣어 AI 번역 후 사람이 검수하는 워크플로우는 기술 문서 현지화에 바로 참고할 수 있습니다.

## [Amazon EKS 고급 컨트롤 플레인 구성하기](https://aws.amazon.com/ko/blogs/tech/eks-advanced-control-plane/)
