## [EKS 컨테이너 메모리 스파이크 추적기](https://techblog.gccompany.co.kr/eks-%EC%BB%A8%ED%85%8C%EC%9D%B4%EB%84%88-%EB%A9%94%EB%AA%A8%EB%A6%AC-%EC%8A%A4%ED%8C%8C%EC%9D%B4%ED%81%AC-%EC%B6%94%EC%A0%81%EA%B8%B0-b0ad2ab4422d)
- 회사: 여기어때
- 본문 요약: EC2에서 EKS로 API를 이관한 뒤, 파드마다 두 시간쯤에 한 번씩 컨테이너 메모리가 500MB 튀었다가 5분 뒤 내려앉는 현상을 넉 달에 걸쳐 추적한 기록입니다. 에러 로그는 한 줄도 없었고 응답도 정상이어서 단서는 그래프 위의 스파이크 하나뿐이었습니다. 이관 당시 파드 메모리 상한은 8GB 검토안에서 4GB로 줄었고(힙 2GB 고정), 같은 커밋에 "톰캣은 압축을 지원하지 않으므로" 접속 로그 처리를 톰캣에서 logback으로 옮기는 변경이 함께 들어가 있었습니다. 처음 의심한 건 힙 바깥 네이티브 메모리였습니다. 다이렉트 버퍼를 회수하는 Cleaner가 `-XX:+DisableExplicitGC` 때문에 마지막 안전장치를 못 쓰고 있었고, `finalize()`에 맡기던 네이티브 자원 반납을 try-with-resources로 옮겨 물리 메모리 점유를 1,543MB→959MB로 낮췄습니다. 실제 개선이었지만 스파이크와는 무관했습니다. 두 번째로 Java 21→25 + Generational ZGC 전환을 시도해 STW를 수십 ms에서 1ms 아래로 줄였지만, 함께 넣은 `-XX:+AlwaysPreTouch` 탓에 기준선만 10%p 올라갔고 스파이크는 그대로였습니다. 가설 일곱 개 중 여섯 개를 지운 뒤 돌파구는 "보는 방식"을 바꾼 데서 나왔습니다. 여러 파드를 합산한 그래프에서는 정각·30분마다 규칙적으로 튀는 것처럼 보였지만, 파드 하나만 떼어 그리자 스파이크가 딱 한 번이었습니다. 규칙성은 합산이 만들어낸 착시였고, 문제는 파드 내부에서 각자의 주기로 벌어지는 일이었습니다. 그제서야 `kubectl exec POD -- ls -laht /로그디렉터리/` 한 줄을 쳐봤고, 접속 로그가 500MB에 도달할 때마다 롤오버되며 생긴 .gz 파일 6개의 생성 시각이 그 파드의 스파이크 6회와 정확히 짝지어졌습니다. 진범은 gzip 버퍼가 아니라 **리눅스 페이지 캐시**였습니다. 500MB 파일을 통째로 읽어 압축하는 동안 파일 전체가 페이지 캐시에 올라오고, 컨테이너 메모리 지표는 이 캐시까지 포함해 집계합니다(로그 수집 사이드카가 같은 파일을 다시 읽어가면서 캐시가 더 오래 머문 영향도 있었습니다). EC2에서 멀쩡했던 이유는 압축의 유무가 아니라 빈도였습니다. logrotate가 하루 한 번 호스트에서 처리하던 일이, EKS에서는 파일이 500MB 찰 때마다(하루 열 번 넘게) 컨테이너 안에서 벌어지게 됐고, 여유 공간은 힙 밖 6GB에서 2GB로 줄어 있었습니다. 8GB였다면 최악 46.3%로 알림 근처에도 못 갔을 값이 4GB에서는 92.5%가 됩니다. 해결책으로는 알림 임계치 상향(90→95%), 파일 크기 축소, 비동기 큐, 로그 양 감축을 모두 검토한 끝에 **압축을 끄고** `maxHistory`를 7일→1일로 줄이면서 `totalSizeCap`을 새로 걸었습니다. 로그는 이미 수집기가 중앙 저장소로 보내 더 오래 보관하고 있었기 때문입니다. 한 서비스에 먼저 적용해 4주를 지켜본 뒤 확대했고, 적용 시점 이후 그래프에서 스파이크가 완전히 사라졌습니다.
- 주목할 point: 세 가지가 특히 값집니다. 첫째, **"여러 인스턴스를 합산한 그래프는 존재하지 않는 주기를 만들어낸다"** — 저자를 두 달간 스케줄러 쪽으로 끌고 간 정각·30분 규칙성은 합산과 30분 눈금이 만든 착시였고, 파드 하나만 떼어 보는 클릭 두 번이 첫 단추였습니다. 둘째, **"증상 둘을 한 사건으로 묶으면 오래 걸린다"** — 며칠 단위로 계단을 오르던 기준선(네이티브 메모리)과 두 시간 단위 스파이크(페이지 캐시)는 애초에 별개였는데 하나로 보고 있었습니다. 주기가 다르면 원인도 다릅니다. 셋째, **"플랫폼을 옮기면 같은 지표라도 측정 범위가 달라진다"** — 압축은 디스크를 아끼는 기능이지 메모리와 무관하다고 여기기 쉽지만, 컨테이너 메모리 지표에는 페이지 캐시가 포함됩니다. 로직은 하나도 안 바꾸고 로그를 누가·얼마나 자주·어디에 쓰는지만 바꿨는데 없던 알림이 울리기 시작했습니다. 이관 체크리스트에 "이 지표는 무엇을 측정하는가, 옮기기 전과 달라졌는가" 한 줄을 넣으라는 제안이 결론입니다. 자기 서비스 점검은 로깅 설정 두 줄이면 됩니다 — 파일명 패턴이 .gz로 끝나는지, 파일 크기 기준값이 수백 MB인지.
