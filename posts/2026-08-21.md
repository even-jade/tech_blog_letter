## [Claude Code Dynamic Workflow 쉽게 이해하기](https://devocean.sk.com/blog/techBoardDetail.do?ID=168424&boardType=techBlog&isShared=Y)
- 회사: 데보션
- 본문 요약: Claude Code의 Dynamic Workflow를 "흐름은 코드로 고정, 작업은 에이전트에 위임"이라는 한 문장으로 정리한 입문 글입니다. 큰 작업을 에이전트 하나에게 통째로 맡기면 컨텍스트가 넘치고 흐름이 모델의 즉흥 판단에 좌우된다는 문제에서 출발합니다. Dynamic Workflow는 `meta` 블록으로 시작하는 평범한 JavaScript 스크립트이고, 본문에서 `agent(prompt, opts)`를 호출하면 서브에이전트가 떠서 작업 결과를 JS 값으로 돌려줍니다. `schema`를 주면 검증된 객체가 반환돼 파싱·재시도가 필요 없고, 에이전트가 죽으면 `null`이 옵니다. 구성 요소는 네 가지 — `agent()`, `pipeline(items, ...stages)`, `parallel(thunks)`, `phase()/log()` — 이고 그 외에 `budget`(토큰 예산), `args`(외부 입력), `workflow()`(하위 워크플로우)가 있습니다. 런타임 상한은 동시 실행 16개, 한 실행당 총 1,000개입니다. 대표 패턴으로 적대적 검증(회의론자 N명이 반박, 과반이 반박하면 폐기), 관점 다양화 검증(정확성·보안·성능·재현성 등 서로 다른 렌즈), 심사위원단, 마를 때까지 반복(loop-until-dry), 멀티모달 스윕, 완전성 비평가를 소개하고, 마지막에 모듈별 버그 탐색 + 발견별 적대적 검증을 하는 완결된 스크립트를 통째로 싣습니다.
- 주목할 point: 설계의 핵심은 `pipeline` vs `parallel` 선택이고, 판별 기준이 명확합니다 — "다음 단계가 이전 단계의 **모든** 항목을 교차 참조하는가?" 예(중복 제거/병합/조기 종료)면 `parallel`(장벽 있음), 아니면 `pipeline`(장벽 없음)이 기본입니다. "그냥 flatten/map/filter가 필요해서"는 장벽의 이유가 되지 못하고, 변환은 pipeline 단계 안에서 하라고 못 박습니다. 또 하나 실무적으로 중요한 전제는 **에이전트는 죽을 수 있다**고 가정하고 쓰는 것입니다 — 예제 코드가 `filter(Boolean)`(단계 실패)과 `verdict?.isReal`(검증 에이전트 실패)로 필터를 두 번 거는 이유입니다. `pipeline`/`parallel` 안에서는 전역 `phase()` 상태가 경쟁할 수 있어 `opts.phase`로 직접 지정해야 한다는 점, 비용이 걱정되면 `budget.remaining()`으로 예산이 마를 때까지 도는 식으로 깊이를 예산에 맡길 수 있다는 점도 실전 팁입니다(단 `budget.total`이 없으면 `remaining()`이 Infinity라 가드 필수). 기본값은 명시적 요청 시에만 실행되며(`ultracode` 키워드 또는 저장한 워크플로우 호출), `/effort ultracode`를 켜면 자동 판단합니다. Claude Code v2.1.154 이상 유료 플랜에서 동작합니다.

- 본문 요약: 개인화 플랫폼 MATCH 시리즈 2편으로, 모델이 내린 결정을 운영자가 실제 업무에서 다루는 접점(MATCH Console)과 AI Assistant(MAI)를 소개합니다. 문제 상황이 구체적입니다 — 마케터가 속성 하나를 확인하려고 데이터 분석가에게 질문하고, 캠페인 한 건을 보내려고 스프레드시트·Braze·Databricks에 같은 값을 반복 입력하고 있었습니다. Console은 이 흐름을 세 공간으로 나눕니다. **Data Explorer**(기술 명칭 + 운영자 표기 명칭·설명·발생 조건을 함께 제공하고, 매일 실제 저장소 컬럼과 스키마를 비교해 Active/Inactive 수집 상태를 표시), **Audience**("The users who"로 시작하는 문장형 조건 빌더로 SQL 없이 대상 정의, 저장 전에 모수와 실제 포함 고객 프로필까지 검증), **Activation**(CRM 캠페인으로 실행하거나, 최종 판단은 하지 않고 "이 유저가 어떤 오디언스에 속하는지"만 알려주는 Audience API로 제공). MAI는 ReAct 기반 에이전트로 ①DB/테이블 목록 조회 ②스키마 확인 ③샘플 데이터 확인 ④SELECT 실행 네 가지 도구를 쓰며, 탐색 과정이 실시간 스트리밍되고 최종 답변과 함께 실행된 SQL도 노출합니다.

- 본문 요약: 선상(선박) 파드에서 육상 데이터 레이크로 메시지를 재전송하는 파이프라인에서, EMQX와 CCMD의 TPS 제한 때문에 순간 폭주 구간을 검증해야 했던 사례입니다. 일반 부하 테스트로는 평균 트래픽만 보게 되어 유실과 회복 시간을 확인하기 어려웠기 때문에, 짧은 시간에 부하를 급증·급감시키는 **스파이크 테스트**를 선택했습니다. 관측 지표는 발행 TPS, 중계 구간의 적체와 에러율, 최종 수신 건수와 시퀀스 번호를 함께 봤고, 이를 통해 병목과 유실 지점을 특정했습니다. 원인은 재발행 로직의 무제한 순차 발행과 즉시 재시도가 중계 구간을 포화시킨 것이었고, 토큰 버킷 기반 속도 제한과 지수 백오프로 개선했습니다.
- 주목할 point: **TPS 제한이 있는 직렬 파이프라인은 평균이 아니라 순간 최대 유입 기준으로 검증해야 한다**는 것이 핵심 교훈입니다. 그리고 부하 발생량을 가상 사용자 수가 아니라 초당 요청 수 기준으로 직접 제어하라는 조언 — VU 수는 응답 시간에 따라 실제 유입량이 흔들리기 때문입니다. 마지막으로 스파이크가 지나간 **회복 구간까지 관측**해 적체 해소 시간과 유실 여부를 함께 확인하라는 점이 실무적입니다. 재시도 로직에 속도 제한과 지수 백오프가 없으면 장애 상황에서 재시도 자체가 2차 폭주를 만든다는, 흔하지만 자주 놓치는 패턴이기도 합니다.

## [LLM 서빙, 띄우는 것과 잘 띄우는 것 사이](https://toss.tech/article/tech_talk_talk_2)
- 회사: 토스(토스증권)
- 본문 요약: 토스증권이 on-premise LLM을 2년간 서빙하며 겪은 문제와 대응 체계를 정리한 글입니다. 출발점은 지표 재정의였습니다 — 기존 ML 모델은 단건 응답 시간과 초당 처리 건수가 핵심이었지만, LLM은 토큰을 순차 생성하므로 **처리량은 초당 생성 토큰 수, 응답 시간은 TTFT(첫 토큰까지의 시간)** 로 바꿨습니다. 여기에 Grafana(메트릭 추이·이상 탐지) + Kibana(단건 로그) + vLLM·SGLang이 제공하는 LLM 전용 지표를 하나의 대시보드로 통합했습니다. 이 체계를 갖춘 뒤에야 원인을 찾을 수 있었던 세 사건을 소개합니다. **①비어 있는 캐시** — 타임아웃 알림이 트래픽 피크와 시간대가 안 맞아 지표를 훑다가 Prefix Cache Hit Rate만 값이 0인 것을 발견, 해당 모델만 Prefix Caching이 기본 비활성화되는 특성이었습니다. 재활성화 후 TTFT가 20초 가까이 걸리던 경우가 약 1/10로 줄고 Hit Rate는 90% 이상. **②완벽한 알리바이** — 메트릭상 이상이 없어 로그로 옮겨가니 `finish_reason`이 `length`, 출력 내용에 `</think>` 스페셜 토큰이 리즈닝 구간이 아닌 content 시점에 등장. vLLM의 알려진 버그였고 워크어라운드 적용 후 에러율 0.2% → 0.02%. **③사라진 처리량** — 증설 요청을 받았지만 KV Cache 사용량이 1%도 안 되는 것을 확인, 동시성 테스트로 20까지 받을 수 있음을 검증해 **자원을 두 배로 늘리지 않고 트래픽 4배**를 받을 근거를 얻었습니다.
- 주목할 point: 세 사건 모두 "지표를 보고 있지 않았다면 발견 자체가 불가능했을" 종류라는 점이 메시지입니다. 특히 사건 3은 모니터링이 곧바로 비용 절감으로 이어진 사례입니다 — GPU 파드 증설은 비싸기 때문에, 증설 전에 "우리가 GPU를 충분히 쓰고 있는가"를 KV Cache 사용률로 먼저 확인하는 절차가 값집니다. 동시에 한계도 솔직합니다: 문제 대부분이 vLLM·SGLang 같은 프레임워크 의존성에 걸려 있어(특정 옵션 조합에서 content 미반환, 설정대로 동작하지 않음, 릴리스 노트를 믿고 적용했더니 CPU 스로틀링) 사전 차단이 아니라 **발견 → 관찰 → 가설과 검증 → 반영과 롤백**의 4단계 루프로 대응한다고 정리합니다. LLM 생태계의 변화 속도를 전부 따라가는 대신, 지표를 넓게 펼쳐두고 빠르게 원인을 좁히는 쪽을 택했다는 결론입니다.

## [VPC Lattice 기반 서비스 네트워크 재설계와 비용 최적화 사례](https://tech.imweb.me/posts/vpc-lattice-kong-service-network/)
- 회사: 아임웹
- 본문 요약: ALB 규칙 증가, ECS Target Group 5개 제한, ALB 체인 확장 불가로 MFE(마이크로 프론트엔드) 서빙 경로가 확장 한계에 도달한 상황에서 서비스 네트워크를 재설계한 사례입니다. 요구사항은 신규 EKS 클러스터와 기존 운영 계정·VPC 경계를 넘는 host/path 기반 라우팅, GitOps 반영, private subnet 유지였습니다. 검증 결과 Lattice를 전 구간 라우터로 쓰는 방식과 ALB·CloudFront 진입점 직접 연결은 불가능했습니다. 최종 구조는 North-South와 East-West를 분리하고 역할을 나눈 형태입니다 — ALB는 기존 진입점 유지, NLB는 계정 경계 통과, Kong은 L7 라우팅, VPC Lattice는 서비스 간 연결. Kong의 HTTPRoute는 ExternalName Service를 거쳐 Lattice 도메인으로 연결되며, Host 재작성과 `X-Forwarded-Host` 전달로 원본 도메인을 보존합니다. GitOps 선언 1개에서 ArgoCD, AWS Gateway API Controller, external-dns가 연쇄적으로 라우팅과 DNS를 생성합니다.
- 주목할 point: 기술 선택의 **기각 사유**까지 적어둔 점이 좋습니다 — Istio는 과도하게 무겁고, ALB 증설은 원인 구조를 바꾸지 못해 배제했으며, NLB는 ALB 뒤에 둘 수 있는 고정 IP 경계 통과 수단이라 남은 선택지였고, Kong은 db-less + Git 선언 반영과 중앙 관리에 적합했습니다. VPC Lattice를 택한 이유도 명확합니다: 서비스 네트워크로 여러 VPC·계정에서 공통 접근이 가능해 **진입점 수 × 앱 수로 곱해지던 연결 구성을 줄일 수 있다**는 것. 성과는 Lattice Service 79개를 14개로 통합해 월 고정비를 82% 절감한 것이고, 이관과 배포 편입도 무중단으로 유지했습니다. 다만 HTTPRoute 1개가 Service 1개에만 대응하는 제약 등 운영상 주의점도 함께 정리돼 있습니다.
