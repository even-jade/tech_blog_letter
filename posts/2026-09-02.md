## [Claude Code 토큰 비용 최적화하기 – 1부: 비용 구조와 세션 습관](https://aws.amazon.com/ko/blogs/tech/claude-code-token-economy-01/)
- 회사: AWS
- 본문 요약: "짧은 한 문장만 물었는데 토큰 사용량이 왜 이렇게 높은가"라는 흔한 질문에서 출발합니다. 답은 단순합니다 — 모델은 요청 사이에 아무것도 기억하지 않으므로 Claude Code는 매 메시지마다 시스템 프롬프트, 프로젝트 컨텍스트, 지금까지의 대화와 도구 결과 **전체**를 다시 전송합니다. 한 턴 안에서 도구를 여러 번 쓰면 그때마다 또 요청이 나갑니다. 즉 **비용은 질문의 길이가 아니라 세션의 크기에 비례**하고, 실제로 지불하는 단가는 **프롬프트 캐싱 적중률**이 정합니다(캐시 읽기 약 0.1배, 표준 입력 1.0배, 5분 TTL 캐시 쓰기 1.25배, 1시간 TTL 2.0배 — 쓰기는 이후 턴의 할인을 사는 1회성 투자). 요청은 시스템 프롬프트 / 프로젝트 컨텍스트(CLAUDE.md·자동 메모리) / 대화의 세 계층으로, 잘 안 바뀌는 것이 앞에 옵니다. 측정 도구 셋을 소개합니다 — `/usage`는 API 과금 사용자에겐 세션 토큰 통계와 추정 비용을, 구독자에겐 플랜 사용량 바와 **어트리뷰션**(서브에이전트·MCP·Skills가 각각 몇 %인지)과 행동 플래그(긴 컨텍스트, 휴식 후 캐시 미스 등)를 보여주고, `/context`는 지금 컨텍스트를 무엇이 점유하는지(MCP 도구 정의가 대화 이력의 절반을 넘는 식) 보여주며, `/insights`는 토큰이 아니라 **일하는 방식**을 최근 세션 최대 200개까지 분석해 HTML 리포트로 냅니다. 캐시 지표 읽는 법도 간단합니다 — read가 creation보다 압도적으로 크면 정상, creation이 턴마다 높으면 프리픽스가 계속 바뀌고 있다는 신호입니다. 컨텍스트 정리는 세 명령의 성격 차이가 핵심입니다: 무관한 작업 전환은 `/clear`(추가 비용 없음, 캐시는 처음부터), 같은 작업인데 컨텍스트가 찼으면 `/compact`(요약 요청 1회 지불 — 캐시가 살아 있을 때 실행해야 싸고, 오래된 세션을 resume한 직후 실행하면 전체 재처리로 가장 비쌈), 방향이 틀렸으면 `/rewind`(**셋 중 유일하게 기존 캐시를 그대로 적중**). auto-compact는 모델별 기본값을 두는 편이 낫고(Sonnet 5는 약 967,000토큰), 윈도우를 낮추면 요약 요청 비용만 누적됩니다. CLAUDE.md는 매 턴 비용을 지불하므로 200줄 이하로 유지하고 상세 지시는 호출 시에만 로드되는 Skills로 옮기라 권합니다(세션 중 파일을 고쳐도 캐시는 안 깨지지만 변경도 반영되지 않으니, 같은 세션에서 반복 수정하며 재시도하는 건 토큰 낭비). 모델·effort는 각각 **별도의 캐시 키**라서 세션 중간에 바꾸면 다음 요청이 전체 미적중이 되고, opusplan은 plan mode를 오갈 때마다 새 캐시를 쌓습니다. 도구 오버헤드 절에서는 MCP 도구 정의가 4.5 세대 이상 모델에서 기본 지연 로딩되지만 custom `ANTHROPIC_BASE_URL` 게이트웨이나 구형 모델 환경에서는 tool search가 죽어 정의 전체가 프리픽스에 실린다는 점, 같은 일을 하는 CLI(`aws`, `gh`)가 있으면 도구 목록 비용이 아예 없다는 점을 짚습니다. 구조적 절약은 서브에이전트(장황한 출력을 격리, 부모 캐시 무손상), Hook(10,000줄 로그를 ERROR 줄만 추려 넘기는 PreToolUse 예시 코드 포함), Skills 순이며, 실험 기능인 에이전트 팀은 plan mode 기준 일반 세션의 **약 7배** 토큰을 씁니다.
- 주목할 point: **"비용은 질문이 아니라 세션의 함수"라는 한 문장이 이 글의 축**입니다. 여기서 실무자가 당장 얻을 건 두 가지 변수 — 컨텍스트 크기와 캐시 적중률 — 로 모든 처방이 환원된다는 정리 자체입니다. 가장 값진 디테일은 **`/rewind`가 셋 중 유일하게 기존 캐시를 적중한다**는 대목입니다. 방향이 틀렸을 때 반사적으로 `/compact`를 누르는 습관은 새 요약을 만들어 캐시를 다시 쌓게 만드는데, 되돌리기는 이미 캐시된 프리픽스로 복귀하므로 훨씬 쌉니다. 두 번째는 **모델과 effort가 캐시 키**라는 사실 — "일단 Sonnet으로 하다가 어려우면 Opus로 올리자"는 자연스러운 습관이 그 시점의 전체 이력 재처리 비용을 부른다는 뜻이고, 그래서 "세션 초반에 정하고 유지"가 캐시 관점의 정답이 됩니다. 세 번째는 **CLAUDE.md를 세션 중에 고쳐도 반영되지 않는다**는 주의사항입니다. 지시가 안 먹힌다고 파일을 반복 수정하며 재시도하는 건 흔한 삽질인데, 실제로는 다음 `/clear`·`/compact`·재시작에서야 로드됩니다. 네 번째는 **Hook으로 LLM이 보기 전에 데이터를 전처리**하는 발상 — 수만 토큰을 수백 토큰으로 만드는 필터는 프롬프트 튜닝보다 훨씬 확실한 절감이고, 이 구조는 Claude Code 밖의 에이전트 설계에도 그대로 옮겨집니다. 마지막으로 **"이 코드베이스 개선해줘" 같은 모호한 요청이 광범위한 스캔을 유발한다**는 지적은, 프롬프트 품질이 곧 비용이라는 걸 가장 알기 쉽게 보여주는 대목입니다.

## [Claude Code 토큰 비용 최적화하기 – 2부: 캐시 경제학과 Amazon Bedrock 조직 비용 관리](https://aws.amazon.com/ko/blogs/tech/claude-code-token-economy-02/)
- 회사: AWS
- 본문 요약: 1부가 개인의 습관이었다면 2부는 **캐시가 언제 살아 있고 언제 깨지는가**, 그리고 **조직이 어디서 비용을 통제하는가**입니다. 캐시 수명(TTL)은 적중할 때마다 타이머가 리셋되므로 계속 작업하는 동안은 만료되지 않습니다. 구독에서는 1시간 TTL을 자동 요청해 한 시간 안쪽 공백을 버티지만, 플랜 한도를 소진해 usage credits 과금으로 넘어가면 5분 TTL로 자동 전환됩니다. API 키·Amazon Bedrock·Google Cloud Agent Platform은 기본 5분이며 `ENABLE_PROMPT_CACHING_1H=1`로 1시간을 선택할 수 있습니다. 무효화 행동 목록이 이 글의 백미입니다 — `/model` 전환, `/effort` 변경, fast mode 첫 활성화(요청 헤더가 캐시 키), MCP 서버 연결·해제, MCP 제공 플러그인 토글, **도구 전체 deny 규칙 추가**(내장 도구 정의가 시스템 프롬프트에서 제거됨. 반면 `Bash(rm *)` 같은 범위 규칙은 무해), `/compact`, Claude Code 업그레이드. 반대로 캐시를 지키는 행동은 저장소 파일 편집, CLAUDE.md·출력 스타일 수정(단 변경도 반영 안 됨), permission mode 전환(opusplan의 plan 토글은 모델 전환이라 예외), Skills·커맨드 호출, `/recap`·`/rewind`·서브에이전트 생성입니다. 가장 비싼 시나리오로 **업그레이드 직후 긴 세션 resume**을 지목합니다 — 대화 이력 전체가 새 시스템 프롬프트 뒤에 놓여 캐시 없이 재처리되므로, 복귀 첫 턴이 그 세션에서 가장 비싼 요청이 될 수 있습니다. 캐시 범위는 사실상 **머신 + 디렉토리 단위**입니다. 시스템 프롬프트에 작업 디렉토리·플랫폼·git 상태가 들어가므로 디렉토리가 다르면 캐시를 공유하지 못하고(같은 저장소의 git worktree끼리도 각자 캐시), 같은 디렉토리에서 나란히 띄운 세션끼리는 서로의 캐시를 읽습니다. 유휴 세션도 공짜가 아닙니다 — scheduled task는 간격마다 전체 컨텍스트를 실어 보내고, cross-session 메시지 수신도 새 턴을 시작하며(`crossSessionInbound`를 hold로), goal 체크인은 `CLAUDE_CODE_GOAL_CHECKIN_MINUTES=0`으로 끕니다. 조직 관리 절은 접속 방식이 통제 지점을 정한다는 표로 정리됩니다: Teams/Enterprise는 spend report(일 단위 CSV)와 usage credits 한도, Console(API)은 자동 생성되는 Claude Code 전용 워크스페이스의 spend limit과 rate limit(Claude Code 트래픽이 프로덕션 API 한도를 잠식하지 않게), Amazon Bedrock 등 클라우드는 클라우드 청구 콘솔과 예산 도구입니다. **클라우드 경유 사용은 Anthropic 대시보드에 잡히지 않으므로**(Claude Code가 메트릭을 보내지 않음) 사용자별 어트리뷰션은 OpenTelemetry(준실시간 자체 관측 스택으로 보내는 유일한 방법), 셀프호스팅 Claude apps gateway, LiteLLM 같은 LLM 게이트웨이(비제휴 오픈소스, 보안 검토는 각 조직 몫) 중에서 선택해야 합니다. 다만 게이트웨이 경유는 캐시 효율을 깎을 수 있는데, 게이트웨이가 `cache_control` 마킹을 그대로 전달하면 직접 연결과 동일하고, 거부하면 시스템 컨텍스트 블록만 미캐시로 과금되며, **조용히 제거하면 대화 이력 전체가 매 요청 미캐시 입력으로 과금**됩니다. Bedrock 특유의 함정도 짚습니다 — 캐시 체크포인트당 최소 토큰이 모델별로 다르고(Fable 5·Opus 5 512, Opus 4.8·Sonnet 5·Sonnet 4.6 1,024, Haiku 4.5 4,096), 미달하면 요청은 성공하지만 캐시는 만들어지지 않는 **조용한 실패**가 됩니다. 체크포인트는 요청당 최대 4개, tools → system → messages 순이라 앞 섹션을 바꾸면 뒤 캐시까지 무효화됩니다. 또 Bedrock 응답의 `inputTokens`는 **비캐시 입력만** 나타내므로 총 입력은 `inputTokens + cacheReadInputTokens + cacheWriteInputTokens`로 합산해야 하고, 캐시 적중분은 rate limit에서 차감되지 않습니다. 마지막으로 증상별 점검표(한 문장 질문에도 사용량이 큼 / 휴식 후 첫 턴이 비쌈 / creation 토큰이 계속 높음 / MCP 추가 후 비용 증가 / Bedrock에서 캐시 토큰이 0 / 유휴 세션 사용량 증가)와 적용 우선순위(①측정 체계 ②컨텍스트 정리 습관 ③모델·effort 조정 ④세션 중 구성 변경 중단 ⑤서브에이전트·Hook·Skills 구조 변경)로 마무리합니다.
- 주목할 point: **"캐시는 프리픽스의 정확한 일치로 동작한다"는 원리 하나로 무효화 목록 전체가 설명된다**는 게 이 글의 구조적 미덕입니다. 개별 항목을 외울 필요 없이 "요청 앞부분을 건드렸는가"만 물으면 됩니다. 실무에서 가장 값진 건 **도구 전체 deny 규칙은 캐시를 깨지만 `Bash(rm *)` 같은 범위 규칙은 깨지 않는다**는 구분 — 권한 정책을 설계할 때 비용까지 함께 고려하게 만드는 디테일입니다. 두 번째는 **캐시가 머신+디렉토리 단위**라는 사실입니다. git worktree로 병렬 작업하는 팀은 워크트리 수만큼 캐시를 따로 쌓고 있다는 뜻이고, 반대로 같은 디렉토리에서 세션 두 개를 띄우면 서로의 캐시를 읽으므로 병렬 전략의 비용 계산이 달라집니다. 세 번째는 **게이트웨이의 트레이드오프를 정면으로 계산에 넣은 것** — 사용자별 어트리뷰션을 얻는 대가로 캐시 효율(과 tool search)을 얼마나 내주는지 세 가지 시나리오로 나눠 설명한 대목은, "일단 게이트웨이 세우자"는 조직의 기본 반응에 제동을 겁니다. 네 번째는 **Bedrock의 조용한 실패** — 최소 토큰 미달 시 에러 없이 캐시만 안 만들어지므로, 캐시 토큰이 0인데 이유를 모르는 상황이 실제로 발생합니다. 여기에 `inputTokens`가 비캐시 입력만이라는 점까지 겹치면 **비용 대시보드가 사용량을 과소 집계**할 수 있다는 경고는 Bedrock으로 운영하는 팀이 오늘 당장 확인해볼 만합니다. 마지막으로 우선순위에서 **측정 체계를 1순위로 두고 "없으면 나머지는 전부 막연한 판단"이라고 못박은 것**, 그리고 서브에이전트·Hook·Skills 같은 구조 투자를 5순위로 미룬 것은, 도구부터 늘리고 보는 흔한 순서를 뒤집는 조언입니다.
