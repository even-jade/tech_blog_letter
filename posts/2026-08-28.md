## [1%가 겪은 버그 고쳐야할까요?](https://toss.tech/article/qa_hotfix)
- 회사: 토스
- 본문 요약: 점진 배포 중 "1% 사용자에게만 보이는 버그"를 두고 핫픽스를 낼지 말지 판단하는 기준을 세우고, 뒤집고, 다시 세운 기록입니다. 원래는 Critical/Major/Minor 심각도 규칙을 썼지만 사용자 수가 많다 보니 낮은 배포율에서 생긴 문제도 실제로는 수많은 사람이 겪었고, 한 화면에 여러 비즈니스 로직이 얽혀 있어 같은 'Major'라도 대응이 갈렸습니다. 그래서 우선순위로 줄 세우는 대신 **지금 고칠 것 / 다음 정기 배포로 넘길 것**의 이분법으로 바꿨습니다. 즉시 핫픽스는 기본 기능 사용 불가·매출 직접 영향·규제 관련 세 가지, 이관은 이용률이 아주 낮은 기능·특정 조건에서만 발생·우회 방법이 분명한 경우입니다. 여기엔 점진 배포 특유의 모순이 있습니다 — "1%니까 안 심각하다"는 판단은 아직 버전을 받지 못한 99%의 잠재 위험을 못 본 것일 수 있고, 반대로 정말 특정 조건의 1%라면 핫픽스가 멀쩡한 99%를 새 빌드 위험에 밀어 넣는 일이 됩니다. 판단은 그 주의 릴리즈 마스터와 QA 마스터 두 사람의 합의로만 배포됩니다. 처음 있던 "2~4시간 버퍼를 두고 다른 이슈도 같이 본다"는 시간 기준은 핫픽스의 목적과 충돌해 폐기하고, 목표 문구도 '어렵고 안전하게'에서 '신중하고 안전하게'로 바꿨습니다. 크래시가 나면 가장 오래 걸리는 건 수정이 아니라 재현이라, Claude 스킬로 만든 `crash-path`가 크래시 URL 하나로 사용자 행동 로그를 시간순으로 되짚어 재현 절차와 기기·OS·메모리 환경까지 한 장으로 정리해 줍니다. Bugsnag(Android)와 Crashlytics(iOS)는 URL만 보고 스스로 구분하고, 화면 이름이나 회귀 판정 같은 판단은 AI 추측에 맡기지 않고 규칙으로 박아 둬 결과의 일관성을 확보했습니다. 관리 쪽에서는 흩어져 있던 iOS/Android 핫픽스 기록을 사내 플랫폼 토션에 한 틀로 모았고, **하지 않기로 한 건도 사유와 함께 쌓습니다**. 사후기록을 일부러 번거롭게 만들면 핫픽스가 줄 거라는 초기 가설은 정반대 결과(핫픽스는 그대로, 기록만 부실)를 낳아 뒤집었고, 지금은 채널 논의 맥락을 AI 봇이 초안에 미리 채워 두고 사람이 보완하는 방식입니다. 매달 Android·iOS·QA가 모여 지난달 핫픽스를 돌아보고 재발 방지 액션을 정하되, 그 액션은 이슈 티켓과 연결돼 티켓이 실제로 닫혔는지를 시스템이 주기적으로 확인해 이행 상태를 자동 갱신합니다(사람이 손으로 "했다"고 체크할 수 없습니다). 원인은 코드 결함·의존성/SDK·배포 실수·환경·외부 API·기타 여섯 가지로 분류해 지표화하고 있습니다.

## [LLM Wiki: 코드 기준으로 자동 최신화되는 도메인 지식 SSOT 만들기](https://techblog.lycorp.co.jp/ko/llm-wiki-code-driven-knowledge-ssot)
- 회사: 라인(LINE Plus)
- 본문 요약: MSA 환경에서 하나의 기능이 여러 서비스에 나뉘어 있어 단일 저장소 코드만으로는 비즈니스 흐름을 알 수 없고, AI가 낡은 문서나 부족한 맥락을 추론으로 메우면 잘못된 스펙이 이후 개발·검토의 기준이 되어버리는 문제에서 출발합니다. 해법은 매번 흩어진 정보를 AI에 주입하는 대신 **코드를 근거로 삼는 SSOT**를 만드는 것. Andrej Karpathy가 제안한 LLM Wiki(원본을 매번 다시 읽는 대신 LLM이 한 번 읽어 위키로 정리해 두고 이후 질문은 위키에서 답하게 하는, 그리고 그 위키를 사람이 아니라 LLM이 관리하는 개념)를 코드 중심으로 구현했습니다. SSOT는 두 층입니다 — `raw`는 코드에서 추출한 현재 동작 기준 스펙과 그 판단의 배경(주석·Confluence·Slack·회의 메모)을 원본 그대로 보존하고, `knowledge`는 그 raw를 LLM이 읽어 지금 기준의 도메인 문서로 재구성한 층입니다. 흐름은 최초 1회 baseline 생성과, 이후 PR 병합마다의 갱신으로 나뉩니다. 추출 스킬은 DTO/Entity에서 데이터 기준, Validator/예외 처리에서 정책·예외, Service/UseCase에서 처리 흐름, YAML/Config에서 한도와 환경차, API·메시지에서 연동 관계, 주석에서 결정 배경을 뽑되 클래스·메서드 구조를 그대로 옮기지 않고 정책·데이터·흐름·예외로 바꿔 적습니다. 단 **API 엔드포인트, Kafka 토픽, DB 컬렉션, enum 값 같은 식별자만은 번역·축약 없이 원문 그대로** 옮깁니다(한 글자만 달라져도 추적이 끊기므로). 코드만으로 판단이 안 서는 지점은 사람에게 물어 확인한 뒤에야 baseline으로 확정됩니다. PR 단위 스킬은 diff에 더해 변경 파일 전체와 주변 참조 코드까지 입력받아 "이전엔 이랬는데 이번에 이렇게 바뀌었다" 형태의 변경 스펙·분석 리포트·리뷰 피드백 정리 세 문서를 만듭니다. `ingest`는 raw를 knowledge에 반영하되 raw는 변경 이력으로 누적하고 knowledge에는 현시점 유효 정보만 남깁니다. knowledge 문서는 사람용/AI용을 나누지 않고 같은 Markdown 하나로 — 앞에 frontmatter(title, doc_type, tags, sources, last_updated)와 TLDR 한 줄을 붙여 AI가 문서 성격·최신성·근거 경로를 빠르게 판단하게 하고, 같은 파일을 HTML로 변환해 사람이 읽는 Knowledge Wiki로 배포합니다. `lint`는 링크·정합성, 식별자 무결성, 최신성, 문서 규칙, 산출물 동기화를 주기적으로 점검하며 그중 식별자 무결성이 가장 중요합니다(읽기 좋게 다듬다 원문 식별자가 변형되면 시스템 기준으로는 다른 의미가 됩니다). 이 모두는 GitHub Actions로 PR 병합을 트리거 삼아 자동 실행되고, 사람은 스펙 PR 리뷰만 담당합니다. 활용은 스펙 주도 개발의 사전 영향도 분석(티켓 등록 시 수정 대상·영향 모듈·충돌 정책을 코멘트로), 스펙 구체화 및 구현(PR엔 전체 스펙이 아니라 코드로 확인 불가한 ADR만 첨부), 사후 영향도 분석(API·Kafka 토픽·DB 스키마 등 서비스 경계를 넘는 연결점 추적)으로 이어집니다.
- 주목할 point: **"문서를 사람용과 AI용으로 따로 만들면 결국 한쪽만 낡아 간다"**는 판단이 핵심 설계 원칙입니다. 하나의 Markdown에 frontmatter+TLDR을 얹어 AI 탐색성을 확보하고 같은 파일을 HTML로 렌더해 사람에게 주는 방식은 지금 당장 따라 할 수 있는 패턴입니다. 두 번째는 **raw/knowledge 2층 분리** — 원본과 이력은 절대 덮어쓰지 않고, 어긋나면 knowledge만 다시 만든다는 규칙이 lint→ingest 재실행이라는 복구 경로를 단순하게 만듭니다. 세 번째는 "비즈니스 관점으로 재서술하되 식별자만은 원문 그대로"라는 예외 규칙과, 이를 lint의 식별자 무결성 검사로 기계가 지키게 한 조합입니다. AI 문서화 자동화가 흔히 실패하는 지점(그럴듯하지만 실제와 미묘하게 다른 이름)을 정확히 겨냥합니다. 남은 수동 단계(baseline의 모호점 확인, 스펙 PR 리뷰)를 숨기지 않고 밝힌 점도 도입 판단에 도움이 됩니다.

## [AWS Lambda의 4가지 실행 모델 – 구조와 선택 기준](https://aws.amazon.com/ko/blogs/tech/aws-lambda-four-execution-models-structure-and-selection-criteria/)
- 회사: AWS
- 본문 요약: 2026년 8월 기준 Lambda라는 이름 아래에는 서로 다른 실행 모델 4가지가 있고, 실행 한도가 15분에서 최대 1년까지 벌어졌다는 것이 출발점입니다. **Lambda Functions**(기존 모델)는 호출 단위 실행·최대 15분·Firecracker microVM 격리이며 호출 사이 환경이 freeze돼 웜 재사용 시 /tmp와 전역 변수가 남지만 상태 유지를 보장으로 가정하면 안 됩니다. **Managed Instances**는 고객 소유 EC2에서 실행하고 Lambda가 운영만 맡는 모델로, freeze 없이 상주하며 한 환경에서 여러 호출이 런타임 워커별로 동시 실행됩니다 — "실행 환경 1개 = 동시 호출 1건" 등식이 깨지므로 전역 변수 오염·스레드 안전성·메모리 누수 전파가 마이그레이션 검토 항목이 되고, 특히 **호출이 타임아웃돼도 코드는 강제 종료되지 않고 백그라운드에서 계속 실행**되어 중복 쓰기·중복 알림을 만듭니다. 과부하 시엔 큐잉 대신 backpressure로 거부하고, 에러 시 복구 없이 컨테이너를 폐기·교체합니다. 자동 scale-to-zero가 없어 트래픽이 없어도 최소 실행 환경(기본 3개)까지만 줄고, 과금은 요청 100만 건당 USD 0.20 + EC2 인스턴스 요금 + 온디맨드 가격의 15% 관리 수수료입니다. **Durable Functions**는 체크포인트와 replay로 하나의 실행을 최대 1년까지 이어갑니다. 프리미티브는 `step`(재시도·진행 추적 내장)과 `wait`(과금 없는 대기) 둘이고, 재개 시 코드는 처음부터 다시 실행되되 완료된 step은 체크포인트 결과로 건너뜁니다 — 따라서 **함수가 결정론적이어야** 합니다. 실행당 durable operation 3,000개와 영속 데이터 100MB는 상향 신청 불가이고, durable execution 시작 호출 속도는 리전당 300 RPS라 요청 하나가 실행 하나를 시작하는 흐름에서는 리전당 500만 건 총량보다 이 진입 상한에 먼저 걸립니다. **MicroVMs**는 Firecracker를 프리미티브로 직접 노출해 핸들러·이벤트 대신 VM마다 전용 HTTPS 엔드포인트에 직접 접속하는 방식이며, 최대 8시간·VM 수준 격리·Dockerfile에서 스냅샷 부팅입니다. 스냅샷은 모든 MicroVM이 공유하므로 고유 ID·시크릿·랜덤 시드는 이미지에 넣지 말고 lifecycle hook에서 시작 후 생성해야 합니다. 기본 2GB/1vCPU에 베이스라인 최대 8GB/4vCPU, 부하 시 4배까지 수직 확장(피크 32GB/16vCPU), ARM64 고정입니다. 서울 리전은 아직 미제공. 글 후반부는 기본 Functions의 설정 축(패키징 zip 압축 50MB·해제 250MB / 컨테이너 10GB, 코드 스토리지 리전당 300GB 상향 불가, 동기 6MB·비동기 1MB 페이로드, 동기 호출 상한은 동시성의 10배, 온디맨드 동시성 기본 1,000, 스케일링 10초당 1,000개, 메모리 128MB~10,240MB로 CPU가 비례해 1,769MB에서 vCPU 1개 상당)을 공식 문서 기준 수치로 정리합니다.
- 주목할 point: 결론 문장이 명료합니다 — **서버리스 설계의 첫 질문이 "메모리를 얼마로 할당할 것인가"에서 "어느 실행 모델에서 시작할 것인가"로 바뀌었다.** 실무에서 바로 걸릴 함정 두 개를 꼭 기억할 만합니다. 첫째, Managed Instances의 타임아웃 후 코드 미종료 — 호출자에겐 이미 실패로 응답했는데 백그라운드 작업이 뒤늦게 완료되며 중복 부작용을 만드는 구조라, context 잔여 시간을 코드에서 직접 확인해 중단해야 합니다. 둘째, **API Gateway 기본 스로틀 10,000 RPS vs Lambda 기본 동시성 1,000**의 미스매치 — 기본값 그대로 조합하면 앞단은 통과시키고 뒷단에서 스로틀링되는 병목이 생깁니다. 그리고 신규 계정은 할당량이 축소된 상태로 시작하므로 부하 테스트가 예상보다 일찍 스로틀되면 이 축소 상태부터 확인하는 것이 순서입니다. Durable Functions vs Step Functions 선택 기준(워크플로우가 비즈니스 로직과 밀결합이면 전자, 여러 서비스 통합·무보수 운영이면 후자)도 실무 판단에 바로 쓸 수 있습니다.

## [Terraform Module에서 Terragrunt Stacks까지 IaC 구조를 다시 나눈 이유](https://medium.com/miridih/terraform-module%EC%97%90%EC%84%9C-terragrunt-stacks%EA%B9%8C%EC%A7%80-iac-%EA%B5%AC%EC%A1%B0%EB%A5%BC-%EB%8B%A4%EC%8B%9C-%EB%82%98%EB%88%88-%EC%9D%B4%EC%9C%A0-8d01c4bbd7db)

- 본문 요약: 10개가 넘는 AWS 계정에서 350개 이상 서비스를 Terraform·Terragrunt로 운영하며 IaC 구조를 다시 나눈 기록입니다. 최종 구조만이 아니라 **되돌린 선택들**을 함께 담은 것이 이 글의 성격입니다. 처음엔 서비스마다 Module 사본이 있어 같은 ALB를 만드는 코드가 여러 디렉터리에 흩어졌고, 시간이 지나며 사본끼리 모양까지 달라졌습니다(어떤 곳은 `alb.tf`, 어떤 곳은 `main.tf`). 공통 Module로 합치자 이번엔 Module 정의와 Live 코드가 같은 저장소에 있어 **공통 Module 수정이 그것을 쓰는 모든 서비스의 Plan에 즉시 나타났습니다.** 변경을 격리하려고 버전 디렉터리(`1.0.0/`, `2.0.0/`)를 만들자 없애려던 중복이 "서비스별 사본"에서 "버전별 사본"으로 이름만 바꿔 돌아왔습니다. 여기서 필요 조건이 분명해집니다 — 같은 리소스를 만드는 코드는 한 벌만, 그러나 그 변경이 모든 사용처에 동시에 적용되지는 않아야 한다. 그래서 Module을 별도 저장소로 분리하고 Git Tag(`?ref=alb/v1.0.0`)로 버전을 고정했습니다. 남은 문제는 "어디까지를 하나의 Module로 볼 것인가"였습니다. 여러 Resource Module을 묶은 Service Module(`ecs-alb-service`)은 결국 전부 제거했는데, ① 하위 변수를 가공 없이 그대로 재선언·전달하는 껍데기 계층이 됐고, ② "ALB 뒤에 ECS를 붙인다"는 **조합의 결정이 Module 버전과 묶여** 조합만 바꿔도 릴리즈가 연쇄됐으며, ③ Module 내부에서 `data` 블록으로 VPC를 직접 조회해 의존 관계가 Terragrunt에 보이지 않았기 때문입니다. 해결은 Terragrunt 1.0의 Stacks를 써서 역할을 네 계층으로 나눈 것 — **Module**(리소스를 어떻게 만드는가), **Unit**(어떤 Module을 어떤 버전으로 실행하는가, Module과 1:1), **Stack/Blueprint**(어떤 Unit을 조합하고 dependency로 잇는가, 인터페이스 재선언 없음), **Instance**(어느 계정·환경에 어떤 값으로 배포하는가). 이제 ECS 구현을 바꾸면 Module을, 리소스를 추가하면 Blueprint를, production CPU 값만 바꾸면 Instance를 수정합니다. 공통 값도 각 `config.hcl`이 `find_in_parent_folders`로 상위를 탐색해 가져오던 방향을 뒤집어 상위(Instance)에서 하위(Unit)로 전달하도록 바꿨습니다. 재사용 단위의 기준도 "조합 개수를 줄이는 것"에서 **"어떤 변경이 발생했을 때 무엇이 함께 움직여야 하는가"**로 옮겨, Module 변경은 Git Tag로 격리하되 Blueprint에는 버전을 두지 않았습니다(버전을 두면 Service Module의 릴리즈 전파를 재현하게 되므로). VPC·ECS Cluster 같은 공유 인프라는 common Stack으로 분리했습니다. 한계도 밝힙니다 — Terragrunt v1.1.0 기준 Stack의 `unit` 블록을 `count`/`for_each`처럼 조건부로 만들기 어려워 Unit 구성이 다르면 Blueprint를 따로 나누고 있고, 다른 트리의 Unit(common Stack의 VPC 등)을 참조할 때는 `.terragrunt-stack/` 경로 중첩 탓에 여전히 경로를 직접 지정합니다.
- 주목할 point: **"이전 구조가 처음부터 잘못됐던 게 아니라, 서비스 규모와 운영 방식이 달라지는 동안 처음 정한 재사용 단위와 변경 경계가 그대로 남아 있었던 것이 문제"**라는 회고가 이 글의 핵심입니다. 공통화 ↔ 변경 격리의 시계추(중복 → 공통화 → 영향 범위 폭발 → 버전 격리 → 중복 재발)를 네 번 돌고 나서야 "둘 중 하나를 고르는 게 아니라 둘 다 가져갈 구조"로 정리한 여정이 그대로 참고 자료입니다. 실무 규칙 두 개가 특히 값집니다 — 첫째, **추상화 계층을 하나 얹기 전에 그 계층이 새 인터페이스를 제공하는지 아니면 기존 인터페이스를 재선언만 하는지 따져볼 것**(후자라면 유지보수 비용만 늘어납니다). 둘째, **의존 관계를 Module 내부 `data` 블록에 숨기지 말고 입력으로 노출할 것** — 숨기면 오케스트레이터가 실행 순서를 알 수 없고 mock_outputs로 전체 Plan을 확인하는 것도 불가능해집니다. 그리고 "재사용 단위는 코드 유사도가 아니라 변경의 경계로 나눈다"는 원칙은 IaC 밖 일반 모듈 설계에도 그대로 적용됩니다.

## [Swift 6 어때요? (1): 스레드, 블록, 태스크](https://tech.channel.io/kr/articles/e0f2391c)
- 회사: 채널톡
- 본문 요약: actor 안에서 RxSwift 체인이 GCD 스케줄러 위에 돌아가는 프로덕션 코드 한 조각에서 시작합니다. 위험해 보이는 조합이지만 "컴파일러가 통과시켜서"가 아니라 "런타임 동작을 알기 때문에" 안전하다고 판단한다는 것이 글의 태도입니다. 2025년 겨울 팀 스터디의 목표는 특이하게도 **"프로덕트 적용이 목표가 아님"**이었습니다 — Swift 6의 data race safety는 컴파일러가 보는 코드까지만 적용되고 RxSwift와의 interoperability는 보장하지 않으므로, 도입 준비 운동이 아니라 SIL·바이너리까지 파고드는 탐구 자체를 목적으로 삼았습니다. 첫 글은 애플 플랫폼이 스레드를 대하는 원리가 세 번 바뀐 역사를 훑습니다. **스레드의 시대**(NSThread)는 개발자가 스레드를 직접 소유·통제했고 코어가 사실상 하나이던 환경에서 통했습니다. 2004년 무렵 멀티코어 전환으로 적정 스레드 수가 기계마다 달라지자 손으로 세는 모델이 무너지고, 2009년 GCD가 **블록의 시대**를 엽니다. 개발자는 스레드 소유를 포기하고 Block을 큐에 던지며, 그 대가로 C에 클로저 문법(blocks)을 확장으로 얹어야 했습니다(N1370·N1451·N2030 세 차례 표준화 시도가 모두 무산돼 지금도 clang 확장으로 남아 있습니다). 여기서 구조적 한계가 나옵니다 — **큐는 블록 안을 볼 수 없습니다.** 블록이 네트워크를 기다리는지 semaphore에 걸렸는지 큐는 모르고, 아는 건 "던져준 스레드가 돌아오지 않는다"뿐이라 선택지는 스레드를 더 만드는 것뿐입니다(thread explosion). 막을 방법이 시스템에 없으니 "semaphore로 큐를 건너 기다리지 마세요" 같은 가이드는 사람의 머릿속 컨벤션으로 남았습니다. **태스크의 시대**는 이 정보를 언어 밖으로 꺼냅니다. 블록이 중간에 멈출 수 없었던 이유는 진행 상태가 전부 스레드 스택에 있었기 때문이고, 기다리는 동안 스레드에서 내려오려면 값을 힙에 보관할 자리와 resume 지점이 필요합니다 — 이는 completion handler로 이미 하던 일이며, 콜백 지옥은 사람이 함수를 손으로 쪼갠 결과였습니다. async/await는 그 쪼개기를 컴파일러에게 넘깁니다. `await`는 장식이 아니라 "여기서 잘라라"는 표시이고, 저자는 `nm | swift demangle`로 함수 하나가 진입부 + `await resume partial function` + `suspend resume partial function`로 실제 분할되고 `swift_task_alloc`·`swift_task_switch` 심볼이 찍히는 것을 확인합니다. 런타임이 무엇을 기다리는지 알게 되자 스레드를 늘릴 이유가 사라져 고정 크기 풀 위에서 태스크를 바꿔 실행합니다. 다만 이 모델은 풀의 스레드가 blocking 없이 forward progress를 만들 때만 성립하며, 표준 라이브러리 소스 주석에도 그 조건이 명시돼 있습니다. 마지막으로 "잘린 조각은 어느 스레드에서 resume되나"라는 질문에 SIL의 `hop_to_executor` 명령이 답이 되고, `work()`가 nonisolated라 목적지가 `none`인 반면 `@MainActor`였다면 메인 스레드가 되는 구조, 그리고 await는 하나인데 조각이 둘인 이유(resume 지점 하나가 곧 절단 지점 하나)까지 짚습니다.
- 주목할 point: **"동시성 문제는 라이브러리 선에서 끝나지 않고 언어를 건드리게 만든다"**는 복선이 2009년(blocks)과 2021년(async/await) 두 번 회수되는 서사가 이 글의 뼈대입니다. 큐가 블록 안을 볼 수 없었던 것도, 함수를 자르는 일도 라이브러리로는 불가능했고 컴파일러만 할 수 있었습니다. 실무 관점에서 가장 중요한 문장은 **"블록 시대의 가이드는 컨벤션, 태스크 시대의 가이드는 계약이되 그 계약의 절반만 문법이 강제한다"**입니다. 기다림을 `await`로 적지 않으면 컴파일이 안 되지만, `await` 대신 스레드를 쥔 채 기다리는 blocking은 컴파일러가 보지 못하고, 고정 크기 풀에서는 blocking 몇 개만 겹쳐도 풀 전체가 설 수 있습니다. Swift 6이 컴파일 에러로 승격시킨 건 data race와 isolation 위반까지라는 경계를 명확히 아는 것이 마이그레이션 판단의 출발점입니다. 스터디 설계 자체도 참고할 만합니다 — "도입"을 목표에서 지우고 동작 이해만 목표로 두자 오히려 파일럿 적용이 뒤따라왔습니다.

- 본문 요약: PC 브라우저에서는 잘 열리는 로컬 개발 서버가 Android Emulator 안에서는 연결에 실패하는 현상의 원인과 해결 순서를 정리한 글입니다. 원인은 서버가 안 떠 있어서가 아니라 **요청을 보내는 환경과 서버가 실행 중인 환경이 다르기 때문**입니다. `localhost`는 특정 장치를 고정적으로 가리키는 이름이 아니라 "현재 요청을 송신하는 시스템 자신"을 뜻하는 호스트 이름이고(IPv4에서 127.0.0.1, IPv6에서 ::1로 해석되는 loopback), PC 브라우저에서는 요청 주체와 서버가 모두 PC에 있어 문제가 없지만 에뮬레이터 안에서는 요청 출발점이 가상 기기 자신이므로 에뮬레이터 자신의 포트를 조회하게 됩니다. 해결의 첫 단계는 에뮬레이터의 가상 네트워크 환경에서 호스트 머신 loopback에 접근하기 위해 제공되는 특수 주소 **10.0.2.2**를 쓰는 것(예: `10.0.2.2:5173`). 다만 이 주소는 에뮬레이터 전용이라 실제 스마트폰에는 통하지 않고, 실물 기기에서는 PC가 로컬 네트워크에서 할당받은 내부 IP(예: `http://192.168.0.10:5173`)를 써야 하며 공유기의 무선 기기 간 통신 차단이나 회사·공용 네트워크의 클라이언트 격리 설정에 막힐 수 있습니다. 주소를 바꿔도 안 되는 경우는 서버 바인딩 문제입니다. 많은 개발 툴이 기본적으로 127.0.0.1에만 바인딩하므로 Vite라면 `vite --host` 또는 `vite --host 0.0.0.0`(0.0.0.0은 접속할 주소가 아니라 "사용 가능한 모든 인터페이스에서 수신"을 뜻하는 바인딩 설정값), package.json 스크립트에서는 `npm run dev -- --host`로 범위를 넓혀야 합니다. 여기에 OS 방화벽·포트 차단은 위 두 단계가 모두 충족된 뒤에도 패킷을 막을 수 있는 **별도의 보안 계층**이라 구분해서 봐야 합니다. 그래서 점검 순서는 ① PC 브라우저에서 localhost:5173으로 서버 구동 확인 → ② 에뮬레이터에서 10.0.2.2 사용 → ③ 서버 바인딩 확인 및 변경 → ④ 방화벽·네트워크 정책 확인입니다. WebView도 에뮬레이터 내부 클라이언트이므로 동일하게 10.0.2.2를 써야 하고, 브라우저는 되는데 WebView만 안 되면 앱의 네트워크 보안 정책·인터넷 권한까지 범위를 넓혀 봐야 합니다. 서버 주소가 코드에 박혀 있다면 환경 변수나 별도 설정값으로 환경별 분리를 권합니다.
- 주목할 point: 핵심은 주소를 외우는 게 아니라 **요청의 출발점과 서버의 위치를 구분하는 사고**입니다. 같은 5173 포트의 하나의 개발 서버라도 PC 브라우저는 `localhost:5173`, 에뮬레이터는 `10.0.2.2:5173`, 실물 기기는 PC 내부 IP로 — 서로 다른 서버가 아니라 같은 서버를 다른 실행 환경에서 바라보는 접근 경로가 다를 뿐이라는 정리가 명확합니다. 실무적으로는 **주소 체계(10.0.2.2) / 서버 바인딩(--host) / OS 방화벽을 세 개의 독립된 계층으로 나눠 순서대로 좁혀가라**는 트러블슈팅 순서가 그대로 체크리스트입니다. 세 가지를 뭉뚱그려 보면 "에뮬레이터에서 안 된다"에서 멈추지만, 나눠서 보면 어느 단계에서 막혔는지가 바로 드러납니다.
